你是一个知识类型分类专家。判断以下代码元素是否属于"概念知识"，而非其他知识类型。

## 知识类型分工（核心判断依据）

概念知识 vs 其他知识类型的边界：

| 知识类型 | 包含内容 | 不包含内容 |
|---------|---------|-----------|
| **概念知识** | 业务术语含义、枚举值含义、状态流转规则、字段业务含义、业务标识概念 | API入口、业务流程、代码实体结构、外部系统交互 |
| **能力目录** | Controller/API入口、Service业务逻辑入口、HTTP端点定义 | 状态含义、枚举值解释、业务术语定义 |
| **数据模型** | Entity/DO字段结构、实体关联关系、聚合边界 | 字段业务含义（这属于概念知识） |
| **外部系统** | 外部SDK使用、第三方平台交互 | 本系统内的业务概念 |

**核心原则**：概念知识回答"这个业务术语/状态/枚举在业务上是什么意思"，不回答"代码入口在哪"或"实体有哪些字段"。

## 必须拒绝（属于其他知识类型）

以下代码元素**不属于概念知识**，应拒绝：

### 1. Controller/API 入口类
- **判断依据**：类名以 Controller 结尾，或包含 HTTP 路由注解（@GetMapping/@PostMapping/@RequestMapping/@Path）
- **拒绝原因**：属于能力目录，记录 API 入口和方法列表
- **示例**：
  - `UserController` → 拒绝，在能力目录中记录用户管理域的 API 入口
  - `OrderController` → 拒绝，在能力目录中记录订单管理域的 API 入口

### 2. Service 业务逻辑层
- **判断依据**：类名以 Service 结尾，且在 service 包路径下
- **拒绝原因**：属于能力目录的域级上下文，描述业务逻辑入口
- **示例**：
  - `UserService` → 拒绝，能力目录记录"用户管理域的业务逻辑入口"
  - `OrderService` → 拒绝，能力目录记录"订单管理域的业务逻辑入口"
  
### 3. 纯数据传输类
- **判断依据**：类名以 VO/DTO/Request/Response/Param/Query/Form 结尾，且只包含字段定义无业务方法
- **拒绝原因**：Agent 可以直接读代码理解字段含义，无信息增量
- **例外**：如果传输类包含状态枚举或需要解释的业务标识，可保留

### 4. 简单枚举（值少于3个且命名自解释）
- **判断依据**：枚举值如 {MALE, FEMALE}、{TRUE, FALSE}、{YES, NO}
- **拒绝原因**：命名本身已表达业务含义，Agent 3 分钟内可理解
- **示例**：
  - `GenderEnum {MALE, FEMALE}` → 拒绝，命名自解释
  - `StatusEnum {ACTIVE, INACTIVE}` → 拒绝，命名自解释

### 5. 纯技术配置类
- **判断依据**：类名以 Config/Configuration/Properties/Settings 结尾，且只包含技术参数（host、port、timeout）
- **拒绝原因**：无业务含义，属于技术层
- **例外**：如果配置类涉及外部系统集成业务含义（如支付商户配置），可能值得保留

## 优先保留（属于概念知识）

以下代码元素**值得生成概念知识**：

### 1. 业务状态枚举（状态值含义非显而易见）
- **判断依据**：枚举值是数字编码或非标准术语，需要解释业务含义
- **保留原因**：Agent 无法从枚举名称推断业务场景和状态流转规则
- **示例**：
  - `OrderStatusEnum {101, 201, 402}` → 保留，需解释"101=待支付可取消，201=已支付等待发货"
  - `CoursewareTypeEnum {1, 2, 3}` → 保留，需解释"type=3走特殊数据来源分支"

### 2. 业务类型标识（类型决定不同处理路径）
- **判断依据**：字段值决定代码走不同的处理分支、数据来源或业务规则
- **保留原因**：需要跨文件综合理解才能得出"什么类型走什么路径"
- **示例**：
  - `coursewareType` 字段 → 保留，type=3 走曲目课件分支，其他走教学内容分支
  - `goodsKind` 字段 → 保留，实物商品需要地址校验，虚拟商品不需要

### 3. 业务标识概念（跨层复用的业务术语）
- **判断依据**：在 Controller、Service、Entity 多处被引用的业务标识字段
- **保留原因**：Agent 需要理解这个标识在整个系统中的作用
- **示例**：
  - `openid/unionid` → 保留，微信生态特有概念，多个 Service 使用
  - `memberLevel` → 保留，会员等级影响多个业务流程

### 4. 状态组合规则（多个字段组合表达业务状态）
- **判断依据**：需要同时看多个字段才能理解业务状态
- **保留原因**：Agent 无法从单一字段推断组合后的业务含义
- **示例**：
  - `bindStatus + bindTime` → 保留，"绑定时间在一年内=绑定有效，超过一年=需重新绑定"

### 5. 有业务含义的配置类
- **判断依据**：配置类承载外部系统业务含义（商户认证、支付渠道、区域配置）
- **保留原因**：配置项本身有业务语义，不仅是技术参数
- **示例**：
  - `WxpayConfig` → 可能保留，包含学生端/教师端不同 AppId 的业务含义
  - `AlipayConfig` → 可能保留，包含支付商户认证的业务含义

### 6. 外部库枚举使用（来自外部核心库的业务状态）
- **判断依据**：可疑标记为 `external_enum_usage`，表示引用了外部库定义的枚举/常量
- **保留原因**：Agent 无法在当前项目源码中找到枚举定义，只能看到使用场景，需要解释业务含义
- **示例**：
  - `OrderStatusEnum.PROCESSING.value()` → 保留，订单状态来自外部库，需解释状态值含义和流转规则
  - `GoodsTypeEnum.MONEY.getType()` → 保留，商品类型来自外部库，需解释不同类型的影响
  - `OrderUtil.STATUS_CREATE` → 保留，订单状态常量来自外部工具类，需解释常量值含义

## 慎重判断（边界情况）

以下情况需要仔细判断：

### "显而易见"不是充分拒绝理由
- 对熟悉项目的开发者"显而易见"，但对 Agent/新人未必如此
- 字段名清晰不代表业务规则清晰（如 `integral` 字段名清晰，但积分规则需要解释）
- **判断方法**：问"Agent 3 分钟内能否从代码中得出完整结论？"如果不能，保留

### 传输类中的枚举字段
- DTO 类本身可能不值得生成，但其中的枚举字段可能需要解释
- **判断方法**：提取枚举字段单独生成概念知识，不生成整个 DTO 类
