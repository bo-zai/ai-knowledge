# 知识类型规格

本文定义 `ai-knowledge/` 知识库中 8 类知识的具体规格，包括每类知识的定义、条目结构、提取方式和生成约束。

本文是需求层文档的延伸，用于约束后续解决方案中知识条目的字段设计和生成流程。

## 通用约定

### 证据引用

所有知识条目中的证据引用应至少包含文件路径，建议包含足以定位到具体代码位置的信息（如行号、函数名或类名）。

引用格式不做硬性规定，但应满足：
- 能唯一标识一处代码位置
- 能让 Agent 通过文件路径和定位信息直接找到对应代码
- 同一个知识库内的引用格式保持一致

### 跨类型引用

知识条目之间可以互相引用。引用时应使用被引用条目的标识（如能力名称、概念名称），而非直接复制被引用条目的内容。

### 通用提取流程

所有知识类型的提取都遵循以下基本流程：

1. **AST 提取**：程序通过仓库的 AST 图谱提取结构化信息（类、方法、注解、import、调用关系、配置文件等）
2. **过滤**：根据各类型的过滤规则排除低价值候选
3. **LLM 生成**：将过滤后的候选信息交给 LLM，生成结构化的知识条目

本文不定义具体的 AST 解析工具、LLM 调用方式和提示词组织方式，这些由后续设计文档定义。

### 受控推断约束

LLM 生成的知识条目中，部分内容属于直接事实（如枚举值列表、HTTP 路径、外键字段），可直接从代码证据确认。另一部分内容属于 LLM 的综合推断（如业务语义描述、聚合边界判断、能力关系类型归类），需要受控推断约束。

受控推断的合格标准：

- 每条推断必须能列出至少一个支撑证据的代码位置
- 推断依据必须来自仓库可见材料，不能基于命名联想、行业常识或缺失反推
- 当证据不足以支撑业务结论时（如无法确定聚合边界、无法判断关系类型），应降级为更确定的形式——记录实体引用关系而非聚合、记录调用链而非业务关系类型
- 以下场景禁止推断：无代码证据的业务背景、产品意图、未来规划、组织规则

### 标签一致性

同一知识库内的标签应保持跨条目和跨生成批次的一致性，否则标签过滤在增量更新后逐渐失效。

标签一致性要求：

- 同一知识库内，语义相同的概念使用相同的标签文本（如统一使用"支付"而非混用"在线支付"）
- 增量更新时，生成程序应先读取现有 `_index.md` 中的已有标签池，新条目的标签应优先从池中复用，只有当现有标签无法覆盖时才创建新标签
- 标签应使用最简短的业务术语形式

### 生成阶段

8 类知识之间存在跨类型引用依赖（如约束知识引用能力目录中的能力名称），因此生成应按阶段进行，确保被引用的名称已确定：

- **阶段 1（基础）**：概念知识 → 数据模型 → 能力目录——按序生成，后者可引用前者的名称
- **阶段 2（引用）**：边界知识、外部系统交互、约束知识、能力关系、跨域业务流程——依赖阶段 1 中的能力名称和概念名称，应在阶段 1 完成后生成
- **阶段 3（投影）**：`_glossary.md` 术语速查表——从概念知识中投影，应在概念知识完成后生成

具体实现方式（如是否支持阶段内并行、错误回退策略等）由后续设计文档定义。

### 知识价值门槛

不是所有从代码中提取的信息都值得沉淀为知识。知识价值门槛的核心判断标准：

**只有当 Agent 通过常规代码检索工具（grep、文件读取、AST 搜索）无法在 3 分钟内独立得出相同结论时，该知识才值得生成。**

知识库的价值在于提供"信息增量"——Agent 自身难以高效获取或综合的信息。如果一条知识只是翻译了代码名称、列出了类名清单、或描述了从代码中显而易见的逻辑，它不增加 Agent 的能力，反而浪费 Agent 加载知识库的 token 预算。

**不值得生成的知识（应被过滤）：**

- 简单枚举：值少于 5 个且命名自解释的枚举（如 `GenderEnum: MALE, FEMALE`），Agent 读源码即可理解
- 操作清单翻译：能力目录中的操作如果只是将方法名翻译为中文，未提供业务流程、分支条件、特殊处理等信息增量
- 工程惯例约束：在任何同类型项目中都会出现的通用约束（如参数非空校验、分页限制、乐观锁），不具备业务特异性
- 代码注释复述：代码中已有清晰注释且 Agent 可直接读取的内容

**值得生成的知识（信息增量来源）：**

- 跨文件综合：需要阅读 3 个以上文件才能拼出的业务全貌（如"支付回调与自动取消的竞态条件"需要同时理解 OrderController 的回调方法、乐观锁机制和 Quartz 定时任务）
- 非显而易见的业务规则：代码中的特殊处理逻辑（如"短信校验代码存在但配置为禁用"、"角色不是互斥的，一个用户可同时拥有多个角色"）
- 外部系统交互细节：SDK 的使用方式、回调处理、配置差异（如"微信支付学生和教师端使用不同 AppId"）
- 跨域业务流程：跨越多个能力域的端到端业务路径

**自检方法**：对每条待生成的知识，问"这条知识为 Agent 提供了什么信息增量？"如果回答是"Agent 3 分钟内可以从代码中得出相同结论"，则不生成。

此门槛适用于所有知识类型。各类型章节中的具体过滤规则是此门槛在该类型下的细化。

### 条目质量标准

所有知识条目，不论类型，都应满足以下质量标准。这些标准定义了"一条知识怎么写对 Agent 有用"。

#### 1. 业务化名称

用业务语言命名，不用代码类名或技术术语。

| 反面 | 正面 | 为什么 |
|------|------|--------|
| CoursewareTypeEnum | 课件类型 | Agent 看到"课件类型"能立刻判断与需求的相关性 |
| OrderStatusEnum | 订单状态 | "订单状态"是需求文档中会使用的术语 |
| UserService.bind | 学生绑定老师 | 用业务动作命名，不用方法名 |

#### 2. 一句话定位

条目开头应有一句话说明"这是什么业务场景下的什么"，帮助 Agent 快速判断是否需要深入。

| 反面 | 正面 |
|------|------|
| 课件类型枚举，定义了课件的分类方式 | 课表中每个练习任务的分类标识，决定了数据来源和属性结构的不同处理路径 |
| 订单状态枚举 | 订单从创建到完成的流转状态标识，控制订单可执行的操作（取消、发货、确认等） |

反面的问题：只是翻译了代码名称，没有增加信息量。正面说明了这个概念在什么场景下起作用、它影响什么。

#### 3. 业务语义描述

解释业务含义，不是翻译代码。Agent 自己能读代码，知识库的价值是提供代码无法直接告诉它的业务理解。

| 反面 | 正面 |
|------|------|
| 系统中定义了六种用户角色：STUDENT、NORMAL_TEACHER、SENIOR_TEACHER、PROVINCE_PROXY、CITY_PROXY、SECOND_LEVEL | 用户角色决定用户可以登录哪个端和执行哪些操作。学生只能登录学生端；普通教师和高级教师可以登录教师端，高级教师拥有查看名下所有学生统计数据的额外权限；省代和市代用于区域管理。注意：角色不是互斥的，一个用户可能同时拥有多个角色 |

反面的问题：Agent 读 `RoleTypeEnum` 的源码就能得到相同信息。正面提供了"角色影响什么"、"角色是否互斥"这些需要跨多个文件综合理解才能得到的信息。

**判断标准**：如果一条描述的内容，Agent 通过读代码 5 分钟内能自己得出相同结论，那这条描述就是废话。

#### 4. 关键区分（按需）

当存在容易混淆的近似概念时，应明确指出区别。不是所有条目都需要，只在存在混淆风险时提供。

| 反面（缺少区分） | 正面（有关键区分） |
|----------------|-------------------|
| 会员：通过 MemberLogDO 判断用户是否是会员 | 会员：通过 MemberLogDO 的 dateBegin/dateEnd 时间范围判断，不是 UserDO 上的标记字段。会员到期后自动失效，不需要显式取消。注意：会员 ≠ 用户角色，教师也可以是会员 |

#### 5. 适用范围

每条知识应说明在什么场景下生效、什么场景下不适用。帮助 Agent 避免把知识误用到不相关的场景。

适用范围不需要长篇说明，一两句话足够：

| 知识条目 | 适用范围 |
|---------|---------|
| 订单状态流转约束 | 仅适用于主订单流程，退款流程有独立的状态机（当前未实现） |
| 微信支付集成 | 仅适用于中国大陆地区的微信支付，不支持境外支付 |
| 课表制定规则 | 仅适用于教师为学生制定周课表的场景，学生自主练习不受此约束 |

#### 6. 代码入口

证据字段应提供足够的导航信息，使 Agent 知道从哪个文件、哪个方法开始读代码。

| 反面 | 正面 |
|------|------|
| 证据：UserService.java | 证据：UserService.java#bind — 绑定逻辑主入口，关键判断在第 437 行的时间比较 |
| 证据：OrderService.java | 证据：OrderService.java#submit — 订单创建主流程，涉及库存扣减（第 540 行）和优惠券核销（第 443 行） |

#### 7. 关联引用

引用相关的其他知识条目，帮助 Agent 扩展理解。引用使用链接格式（见 03-knowledge-directory-structure.md）。

#### 8. 标签

每条知识应附带 1~3 个标签，用于分类和检索。标签从条目涉及的业务概念、能力域或关键术语中提取，不使用代码类名。

标签的作用是让 Agent 在扫描 `_index.md` 时，能通过标签快速匹配与当前需求相关的条目，减少不必要的文件加载。

"每条知识"的粒度对应知识库中的一个独立文件。对于能力目录，标签同时出现在两个层级：能力域标签出现在 `_index.md` 中（用于快速筛选域），操作标签出现在域文件内部的操作条目中（用于 Agent 精确定位操作）。

| 反面 | 正面 | 为什么 |
|------|------|--------|
| OrderService, submit, POST | 订单、交易、购买 | Agent 匹配业务需求时用业务术语，不用代码名称 |
| 教学, 管理, 系统, 功能, 模块 | 课表、课件、教学 | 标签过多等于没有标签，每个标签应反映核心主题 |

## 1. 能力目录知识

### 定义

能力目录是仓库内可见业务能力域的概览，提供域级业务上下文和入口导航。它回答"仓库能做什么"、"各域的业务特点是什么"和"入口在哪"。

能力目录的定位是**域级导航和业务上下文**，而非详细的业务流程描述。域级业务上下文帮助 Agent 快速判断一个需求是否属于该域、该域有哪些特殊业务机制。详细的业务流程、约束和概念由其他知识类型（约束知识、概念知识、能力关系等）承载。

### 结构

能力目录采用两层结构：能力域（一级）和操作条目（二级）。

**能力域**代表一个业务能力分组，通常对应一个 Controller 类、路由模块或 Handler 组。能力域包含：

- 域名称：业务化的能力分组名称（如"订单管理"、"教学管理"）
- 域描述：说明该能力域覆盖的业务范围
- 域级业务上下文：该域的核心业务规则、关键机制或特殊处理逻辑的简要说明。帮助 Agent 理解该域的业务特点，而非仅知道有哪些操作。域级上下文是补充性信息，不替代其他知识类型中的详细条目
- 适用范围：该能力域适用的业务场景和不适用场景
- 标签：用于分类和检索的关键词（1~3 个），从该域整体业务含义中提取
- 入口类/模块：对应的代码类或模块位置
- 操作条目列表：该域下的所有操作，作为入口导航索引

**操作条目**代表一个具体可触达的操作，通常对应一个 HTTP 端点方法、RPC 方法或消息处理函数。操作条目包含：

- 操作名称：业务化的操作名称（如"创建订单"、"制定课表"）
- 访问方式：HTTP 方法和路径（如 `POST /order/submit`），非 HTTP 入口标注其协议类型
- 方法位置：入口方法所在的类和方法名
- 操作描述：一句话说明该操作的业务目的
- 标签：用于分类和检索的关键词（1~3 个），从操作涉及的业务概念中提取
- 输入输出摘要：关键参数类型和返回类型（不做详细说明）

### 产物示例

```
## 订单管理

域描述：商品购买的订单全生命周期管理，包括创建、支付、取消、查询和再次购买。
域级业务上下文：订单支持支付宝、微信和余额三种支付渠道，支付回调与定时任务均可触发状态变更，存在竞态条件需乐观锁保护。订单状态由状态码（101~402）驱动，不同状态控制可执行的操作集合。
适用范围：仅适用于实物商品和虚拟商品的购买订单，不适用于退款流程。
入口类：OrderController

| 操作名称 | 访问方式 | 方法位置 | 描述 | 标签 |
|---------|---------|---------|------|------|
| 创建订单 | POST /order/submit | OrderController.submit() | 提交商品购买订单，完成商品校验、库存扣减和优惠券核销 | 订单、创建、购买 |
| 取消订单 | POST /order/cancel | OrderController.cancel() | 取消未发货订单，回滚库存和优惠券 | 订单、取消、库存 |
| 查询订单 | GET /order/detail | OrderController.getDetail() | 查询单个订单详情，包含订单商品和物流信息 | 订单、查询 |
| 订单列表 | GET /order/list | OrderController.queryOrder() | 分页查询用户订单列表，支持按状态筛选 | 订单、列表、状态 |
| 再次购买 | POST /order/repurchase | OrderController.repurchase() | 将已完成订单的商品重新加入购物车 | 购物车、复购 |

域标签：订单、交易、购买
```

### 提取方式

1. **AST 提取入口候选**
   - 扫描所有可能的入口定义：HTTP 端点注解/路由定义、RPC 接口声明、消息处理函数、定时任务入口、事件监听器等
   - 提取入口的访问方式（HTTP 方法+路径）、方法签名、参数类型、返回类型
   - 不限定具体框架，通过 AST 中的注解、路由定义、函数签名等结构特征识别入口

2. **AST 分组**
   - 按入口所在的类或文件路径自动分组
   - 分组依据代码的物理组织结构（包路径、文件目录）

3. **LLM 生成**
   - 为每个分组生成业务化的域名称、域描述和域级业务上下文
   - 为每个操作生成业务化的操作名称、操作描述和标签
   - 域级业务上下文基于操作列表和代码结构综合生成，提炼该域的核心业务规则和特殊机制
   - LLM 只负责命名和描述，不判断分组归属

### 生成约束

- 能力目录应覆盖仓库中所有可被外部触达的入口
- 工具类、配置类、基础设施类等非业务入口不列入能力目录
- 操作描述应说明业务目的，不描述实现细节
- 操作描述中，如涉及特定角色的访问限制（如权限注解、角色判断逻辑），应在描述中提及角色名称（如"仅教师可操作"），帮助 Agent 理解操作的访问边界
- 域级业务上下文应提炼该域的核心业务机制和特殊规则，不是操作描述的简单拼接。好的域级上下文提供跨操作的综合洞察（如"支付回调与定时任务存在竞态"），而非逐一列举每个操作的特点
- 域级业务上下文不超过 2~3 句话，避免与约束知识、概念知识的内容重叠

## 2. 概念知识

### 定义

概念知识记录仓库中可见的业务概念的定义和业务含义。它回答"这个术语/状态/枚举/字段在业务上是什么意思"。

不是所有代码元素都需要成为概念知识。只有满足以下至少一个条件的代码元素才值得沉淀为概念知识：

- 需求文档中可能出现该业务术语
- 代码名称不能直接表达业务含义（如枚举值含义非显而易见）
- 存在容易误解的业务语义

### 结构

一条概念知识包含：

- 概念名称：业务化的概念名称（如"用户角色"、"订单状态"）
- 业务含义：该概念在业务上的定义和解释
- 别名（可选）：该概念在需求文档或代码中的其他叫法，包括中文业务术语（如"购物车"）和代码英文命名（如 `Cart`、`ShoppingCart`），用于提升 Agent 在需求澄清和代码检索时的命中率
- 适用范围：该概念适用的业务场景和不适用场景
- 代码体现：该概念在代码中的具体表现（类名、枚举名、字段名）
- 值说明（适用于枚举/状态类概念）：
  - 5 个值以内：逐值解释业务含义
  - 6~15 个值：列出所有值名，只解释业务含义非显而易见的值
  - 15 个值以上：描述整体分类逻辑，不逐值展开
- 关键区分（可选）：与名称相近但含义不同的概念的区分说明
- 关联概念（可选）：与本概念存在业务关联的其他概念
- 标签：用于分类和检索的关键词（1~3 个）

### 产物示例

```
## 课件类型

概念名称：课件类型
业务含义：课表中的课件分为两种类型，它们走不同的数据来源和属性结构。
  - type=3（PRACTICE_MUSIC）：曲目课件，数据来自 TeachCategoryCourse，包含节拍（beat）、和弦（chord）属性
  - 其他类型：教学内容课件，数据来自 TeachCategoryContentCourse，额外包含节奏（rhythm）、列表类型（listType）属性
  两种课件在课表展示、学习统计和打分流程中走不同的处理路径。
代码体现：CoursewareDO.coursewareType（字段）+ CoursewareTypeEnum（枚举）
适用范围：仅适用于课表中的课件任务，不适用于学生自主练习场景下的练习内容
别名：课件分类、练习类型
关联概念：教学分类、课表
标签：课件、教学、课表
```

### 提取方式

1. **AST 提取候选**
   - 所有枚举类
   - 核心业务实体类（排除 DTO、VO、Request、Response 等传输类）
   - 常量类中具有业务含义的常量组（以业务前缀命名的常量，排除纯技术配置如超时时间、连接池大小等）
   - 状态枚举相关的状态流转代码（扫描包含状态变更赋值的 Service 方法，提取状态之间的合法转换路径）
   - 自定义业务注解或装饰器的定义和使用（排除框架内置注解如 `@Override`、`@Autowired`）

2. **多模块依赖处理**
   - 扫描项目构建配置（pom.xml、build.gradle、go.mod 等），识别对外部模块（同项目其他子模块、公司内部 JAR/包）的引用
   - 当代码中使用的实体类（DO/Entity/Model）定义在外部模块时，标注为"外部模块实体"
   - 外部模块实体在后续步骤中仍可作为概念知识的候选，但证据中标注所属模块（如 `music-core`）
   - 如果外部模块也在仓库中（多模块项目），一并解析其源码

3. **过滤**
   - 按命名模式过滤：排除名称中包含 Util、Helper、Common、Base、Abstract、Config、Property 等工具/基础设施特征的类
   - 按包路径过滤：排除位于 util、common、config、infrastructure、framework 等非业务包下的类
   - 按类名后缀过滤：排除 *DTO、*VO、*Request、*Response、*Param、*Query、*Page 等传输类
   - 自定义注解过滤：排除名称中包含 Log、Cache、Trace、Metrics、Monitor 等纯技术特征的注解，只保留有业务语义的注解
   - 常量组过滤：排除无业务前缀的零散常量，只保留命名中包含业务领域标识的常量组
   - 复杂度门槛：排除代码本身已充分表达含义的简单元素——值少于 5 个且命名自解释的枚举（如 `GenderEnum: MALE, FEMALE`、`BooleanEnum: TRUE, FALSE`），Agent 读源码即可理解，不需要额外的知识条目

4. **LLM 生成**
   - 从通过过滤的候选中，LLM 判断哪些属于同一个业务概念并合并
   - 为每个业务概念生成条目内容
   - LLM 决定粒度：一个代码元素可能独立成条，也可能与其他元素合并为一个概念
   - LLM 的合并判断应基于代码中的显式引用关系（如一个 Service 方法同时操作多个相关类），而非语义猜测

### 生成约束

- 概念知识只沉淀有代码证据支撑的业务含义，不推断代码中不可见的业务背景
- 值说明中，如果枚举值名称本身已清晰表达含义（如 `ORDER_CANCELLED`），不需要额外解释
- 关联概念只引用名称，不复制被引用概念的内容
- LLM 合并概念时，必须引用代码中的显式关联作为依据

## 3. 边界知识

### 定义

边界知识记录已有能力的局限性和仓库边界的特殊说明。它不是一份"缺失能力清单"——Agent 可以从能力目录中"没有某个能力"直接推断缺失，不需要显式列出。

边界知识聚焦于 Agent 无法从能力目录直接推断的两类情况：

- **已有能力的局限性**：能力目录中某个能力的范围限制（如"支付只支持支付宝和微信，不支持其他渠道"）
- **被禁用的功能**：代码中存在实现但配置关闭的功能（如"短信校验功能代码存在，但 `smsCheckSwitch` 配置为 false"）

### 结构

一条边界知识包含：

- 边界标题：简短描述边界内容
- 边界类型：局限性 / 禁用功能
- 详细说明：该边界的具体描述
- 适用范围：该边界适用的场景，以及不受该边界限制的情况
- 标签：用于分类和检索的关键词（1~3 个）
- 关联能力（可选）：该边界影响能力目录中的哪些能力
- 证据：支撑该边界结论的代码或配置位置

### 产物示例

```
## 支付渠道局限

边界标题：支付渠道局限
边界类型：局限性
详细说明：当前只支持支付宝和微信支付两个渠道，不支持银联、信用卡或其他支付方式。
  支付宝和微信支付分别有学生端和教师端独立的 AppId 配置，两个端使用不同的支付商户号。
关联能力：订单管理
证据：AlipayConfig.java, WxpayConfig.java, wxpay.properties
适用范围：仅影响支付渠道选择，不影响订单创建和商品管理
标签：支付、渠道

## 短信校验已禁用

边界标题：短信校验已禁用
边界类型：禁用功能
详细说明：系统配置了短信校验开关（mall.global.smsCheckSwitch），当前值为 false。
  短信校验相关代码存在但未被启用，新增涉及手机号验证的功能时需注意此开关状态。
关联能力：用户管理
证据：application.yml#mall.global.smsCheckSwitch
适用范围：仅影响需要手机号验证的新增功能，不影响已有的登录和绑定流程
标签：短信、校验、配置
```

### 提取方式

1. **AST 扫描配置**
   - 识别配置文件中的 feature flag、switch、enable 等开关类配置
   - 检查开关对应的代码实现是否存在
   - 标记"代码存在但可能禁用"的功能

2. **LLM 分析能力域的范围限制**
   - 输入：每个能力域的操作条目列表和使用的技术栈
   - LLM 从已有能力域中识别范围限制（如"支付域只集成了支付宝和微信 SDK"）
   - 这种分析是基于已有代码的总结，不是对缺失能力的猜测

3. **LLM 生成**
   - 综合以上信息，生成边界知识条目
   - 条目数量应少而精（典型项目 5~15 条）

### 生成约束

- 不从能力目录中简单取反生成缺失清单
- 每条边界知识必须说明对 Agent 后续工作的影响
- 禁用功能的判断依据必须来自配置文件的显式值，不来自 LLM 推测
- 局限性描述必须基于已有代码的总结（如"已集成的 SDK 列表"），不基于 LLM 对缺失功能的猜测

## 4. 外部系统交互知识

### 定义

外部系统交互知识记录当前仓库与外部系统之间的可见交互。

外部系统是指当前仓库代码库之外的系统或平台，包括同业务线的其他微服务、第三方业务平台、外部业务数据源和第三方平台服务（如对象存储、短信服务、地图服务等）。不包括当前仓库内部的模块、工具库、消息队列、配置中心等基础设施依赖，除非它们承载了明确的跨仓库业务交互通道。

知识库不描述外部系统内部行为，也不推断外部系统的真实业务责任。

### 结构

一条外部系统交互知识包含：

- 外部系统名称：该外部系统的名称（如"微信支付"、"阿里云 OSS"）
- 交互目的：当前仓库与该外部系统交互的业务目的
- 适用范围：该交互适用的业务场景（如"仅中国大陆地区"）
- 标签：用于分类和检索的关键词（1~3 个）
- 交互方式：通过什么方式交互（SDK、HTTP API、回调入口、数据交换等）
- 当前仓库角色：调用方、被调用方、数据生产方、数据消费方
- 交互入口（可选）：发起交互或接收交互的代码位置
- 可见交互范围：从代码中可以确认的交互操作列表（如"创建支付订单"、"查询支付状态"、"接收支付回调"）

### 产物示例

```
## 微信支付

外部系统名称：微信支付
交互目的：学生端和教师端的在线支付
交互方式：SDK（ijpay-wxpay）
当前仓库角色：调用方（发起支付）+ 被调用方（接收支付回调）
交互入口：WxPayServiceImpl, AbstractWxPayApiController
可见交互范围：
  - 统一下单（创建支付订单）
  - 订单查询（查询支付状态）
  - 接收支付结果回调
适用范围：仅适用于中国大陆地区的微信支付，不支持境外支付
标签：支付、微信、第三方
```

### 提取方式

1. **AST 扫描外部依赖**
   - 扫描项目依赖声明（pom.xml、package.json、go.mod、requirements.txt 等）中的第三方包
   - 扫描 import/require 语句中的外部包引用
   - 扫描 HTTP client 使用（各种语言和框架的 HTTP 客户端调用）
   - 扫描 RPC/gRPC 客户端初始化和调用

2. **配置文件扫描**
   - 扫描配置文件中的非本地 URL、hostname、端口
   - 扫描 API Key、AppId 等外部服务凭据配置
   - 扫描服务注册/发现配置中的外部服务名

3. **AST 定位交互代码**
   - 定位使用了外部 SDK 或 HTTP client 的 Service/Controller 方法
   - 定位接收外部回调的 Controller/Handler

4. **LLM 生成**
   - 汇总以上信息，归纳为"与哪个外部系统交互、目的、角色"
   - 为每个外部系统生成一条交互知识

### 生成约束

- 只记录从代码和配置中可见的交互，不推断外部系统的内部行为
- 可见交互范围只列出从代码中可以确认的操作，不猜测外部系统提供的全部能力
- 基础设施依赖（数据库、缓存、消息队列、配置中心）不作为外部系统记录，但如果它们是仓库与外部系统交互的通道（如通过消息队列向下游发送事件），应记录其作为通道的存在

## 5. 约束知识

### 定义

约束知识记录由代码、配置、测试、注释或已有文档明确体现的业务约束和技术约束。它回答"系统中有哪些必须遵守的规则"。

约束知识不包含通用参数校验（null check、空字符串检查、类型校验）和框架层约束（ORM 注解、序列化配置），只记录有业务含义的约束。

### 结构

一条约束知识包含：

- 约束名称：简短描述约束内容
- 约束类型：业务规则 / 技术约束 / 数据约束
  - 业务规则：由业务逻辑决定的规则（如"教师端不支持微信登录"、"学生绑定老师一年只能一次"）
  - 技术约束：由技术实现决定的规则（如"订单创建使用 Redis 防重"、"库存扣减使用乐观锁"）
  - 数据约束：由数据结构决定的规则（如"用户删除是软删除"、"订单号由雪花算法生成"）
- 约束描述：该约束的具体内容和触发条件
- 适用范围：该约束适用的业务场景和不适用场景
- 标签：用于分类和检索的关键词（1~3 个）
- 作用范围：该约束影响哪些能力或业务概念
- 违反后果（可选）：违反该约束时会发生什么（如抛出什么异常、返回什么错误码）
- 证据：支撑该约束的代码位置

### 产物示例

```
## 学生绑定老师频率限制

约束名称：学生绑定老师频率限制
约束类型：业务规则
约束描述：同一个学生一年内只能绑定一次老师。如果上次绑定时间在一年内，拒绝重新绑定。
作用范围：学生绑定老师（UserService.bind）
违反后果：抛出 UserException("同一个用户一年之内只能绑定一次")
证据：app/service/user/UserService.java#bind
适用范围：仅适用于学生主动绑定老师的场景，管理员后台调整不受此限制
标签：师徒、绑定、频率限制

## 实物商品必须填写收货地址

约束名称：实物商品必须填写收货地址
约束类型：业务规则
约束描述：当商品类型为实物（goodsKind == 1）时，订单提交必须提供有效的收货地址。虚拟商品不要求地址。
作用范围：订单提交（OrderService.submit）
违反后果：抛出 OrderException(ORDER_ADDRESS_ERROR)
证据：app/service/mall/OrderService.java#submit
适用范围：仅适用于订单创建时的地址校验，后续修改订单不触发此约束
标签：订单、地址、实物商品
```

### 提取方式

1. **AST 提取约束候选**
   - 扫描异常抛出语句（throw / raise / panic / errors.New 等）
   - 扫描包含业务判断的条件语句（if...throw、guard 语句等）
   - 扫描事务注解/声明（@Transactional 等）
   - 扫描数据库 schema 约束（NOT NULL、UNIQUE、外键、CHECK 等）
   - 扫描测试中的断言（assert / expect）

2. **过滤**
   - 排除通用参数校验：null check、空字符串检查、类型校验、长度校验
   - 排除框架层约束：ORM 注解、序列化配置、HTTP 状态码
   - 保留业务约束：使用业务错误码的异常、包含业务判断条件的校验、业务状态流转约束
   - 过滤规则：如果异常使用的是通用错误码（如 PARAM_ERROR、INVALID_REQUEST），排除；如果使用的是业务错误码（如 USER_BIND_TEACHER_EXIST、GOODS_NO_STOCK），保留
   - 非通用性过滤：排除在任何同类型项目中都会出现的工程惯例约束，只保留具有业务特异性的约束。判断标准——如果把这个约束放到另一个同业务领域的开源项目中仍然成立，那它是工程惯例，不是业务约束。常见应排除的工程惯例：通用参数非空校验、分页参数范围限制、乐观锁版本号机制、事务回滚策略

3. **LLM 生成**
   - 从过滤后的候选中，LLM 判断约束类型并生成描述
   - 合并同一业务场景下的多个约束为一条（如"订单创建"的多个校验条件合并为一条约束知识）
   - 关联到能力目录中的相关能力

### 生成约束

- 约束必须有代码证据支撑，不输出推断的约束
- 约束描述应说明"什么条件下触发"和"触发后发生什么"
- 同一业务流程中的多个约束应合并为一条，避免过度碎片化

## 6. 能力关系知识

### 定义

能力关系知识记录仓库内可见业务能力之间的组合、依赖、上下游或共享概念关系。它回答"这些能力之间是怎么关联的"。

能力关系只记录业务 Service 层之间的关系，不记录 Service 到 DAO/Mapper 的调用、Service 到工具类的调用、Service 到基础设施（缓存、日志）的调用。

### 结构

一条能力关系知识包含：

- 关系名称：简短描述该关系
- 关系类型：
  - 调用依赖：能力 A 在执行过程中直接调用能力 B（如"课表制定依赖师徒关系校验"）
  - 触发链：能力 A 执行后同步触发能力 B（如"课表制定触发积分发放"）
  - 异步触发：能力 A 通过事件总线或消息机制异步触发能力 B（如"录音打分通过 EventBus 异步触发最高分更新"）
  - 共享实体：能力 A 和能力 B 操作同一个业务实体（如"订单管理和购物车共享商品库存实体"）
  - 组合：能力 A 组合了能力 B、C、D（如"订单提交组合了购物车结算、优惠券验证、库存扣减"）
- 参与能力：关系涉及的能力名称（引用能力目录中的条目）
- 关系描述：该关系的具体说明
- 适用范围：该关系成立的前提条件和不适用场景
- 标签：用于分类和检索的关键词（1~3 个）
- 证据：支撑该关系的代码位置（调用方方法、被调用方方法、共享实体类等）

### 产物示例

```
## 课表制定触发积分发放

关系名称：课表制定触发积分发放
关系类型：触发链
参与能力：课表制定（教学管理）→ 积分管理（运营管理）
关系描述：教师为学生制定课表后，每周首次制定会触发积分发放。如果该学生本周已被制定过课表，不再重复发放。
证据：CourseService.makeTimetable() → CourseService.trySendIntegralOfMakeTable() → OperationService.addUserScore()
适用范围：仅适用于教师为学生制定课表的场景，修改已有课表不触发积分
标签：课表、积分、触发链

## 订单提交组合多个子能力

关系名称：订单提交组合多个子能力
关系类型：组合
参与能力：订单提交 → 购物车结算 + 优惠券验证 + 库存扣减 + 地址校验
关系描述：订单提交过程中依次调用购物车服务获取商品、优惠券服务验证和核销优惠券、商品服务扣减库存、地址服务校验收货地址。任一子能力校验失败则整体回滚。
证据：OrderService.submit() → cartService, couponVerifyService, productService, addressService
适用范围：仅适用于订单提交流程，单独操作购物车或查询优惠券不触发此组合
标签：订单、购物车、优惠券、组合
```

### 提取方式

1. **AST 构建调用图**
   - 从能力目录中已识别的入口出发
   - 追踪业务 Service 之间的方法调用链（深度限制为 2~3 层）
   - 排除 Service → Mapper/DAO 的调用
   - 排除 Service → 工具类（日期、JSON、字符串等）的调用
   - 排除 Service → 基础设施（缓存、日志、配置）的调用

2. **AST 识别共享实体**
   - 多个 Service 注入同一个 Mapper 的情况
   - 多个 Service 操作同一个 DO/Entity 类的情况

3. **AST 扫描事件机制**
   - 扫描事件发布/订阅注解（如 `@EventListener`、`@Subscribe`、`ApplicationEvent` 等）
   - 通过事件类型名称关联发布方和订阅方，作为异步触发关系的补充提取来源
   - 扫描接口注入点，将接口调用解析到实际实现类，补充调用依赖关系

4. **LLM 生成**
   - 从过滤后的调用图和共享实体信息中，LLM 判断关系类型
   - 合并同一业务场景下的多条调用边为一条关系知识
   - 生成关系描述和关联的能力引用

### 生成约束

- 关系必须有代码证据支撑（调用链或共享实体），不推断逻辑上不存在的关联
- 调用依赖只记录业务 Service 层，不记录工具类和基础设施层
- 同一次业务流程中的多条调用关系应合并为一条关系知识，避免逐条记录导致碎片化
- 能力关系基于 AST 静态分析，存在结构性盲区：反射调用、AOP 织入和部分动态调度场景可能无法覆盖。Agent 在分析能力影响范围时，应结合代码搜索工具补充验证

## 7. 数据模型知识

### 定义

数据模型知识记录仓库内核心业务实体之间的关联关系。它回答"实体之间是怎么关联的"、"哪些实体共同构成一个业务聚合"。

数据模型知识关注的是实体间的结构关系（一对一、一对多、多对多、聚合、组合），不关注单个实体的字段详情——字段细节属于概念知识或 Agent 直接读代码。

### 结构

一条数据模型知识包含：

- 聚合名称：该业务聚合的名称（如"课表"、"订单"）
- 聚合描述：该聚合覆盖的业务场景
- 适用范围：该聚合适用的业务场景，以及该聚合不覆盖的相关数据
- 标签：用于分类和检索的关键词（1~3 个）
- 核心实体：聚合中的根实体和子实体
- 实体关系：实体之间的关联方式和关联字段
- 关联其他聚合（可选）：该聚合中的实体与哪些其他聚合的实体存在引用关系
- 证据：实体类和关联字段的代码位置

### 产物示例

```
## 课表聚合

聚合名称：课表
聚合描述：教师为学生制定的周学习计划，包含每天的课程安排和具体课件任务。
核心实体：
  - CourseDO（课程/日维度）：一天的课程安排，包含学生、教师和日期
  - CoursewareDO（课件/任务维度）：一天课程中的具体练习任务，包含课件类型、练习次数和完成进度
实体关系：
  - CourseDO → CoursewareDO：一对多（一天课程包含多个课件任务）
  - CoursewareDO → TeachCategoryCourseDO 或 TeachCategoryContentCourseDO：多对一（课件引用教学内容，根据 coursewareType 决定引用哪个）
关联其他聚合：
  - 引用「教学分类」聚合中的 TeachCategoryCourseDO 和 TeachCategoryContentCourseDO
  - 引用「用户」聚合中的 UserDO（通过 studentId 和 teacherId）
证据：core/DO/CourseDO.java, core/DO/CoursewareDO.java
适用范围：仅适用于教师制定的课表场景，学生自主练习记录不在此聚合内
标签：课表、课程、课件

## 订单聚合

聚合名称：订单
聚合描述：用户购买商品产生的交易记录，包含订单信息、订单商品和支付状态。
核心实体：
  - OrderDO（订单）：订单主体，包含订单号、用户、金额、状态
  - OrderGoodsDO（订单商品）：订单中的具体商品项
  - OrderRecordDO（订单记录）：用户对某个商品的购买累计记录
实体关系：
  - OrderDO → OrderGoodsDO：一对多（一个订单包含多个商品项）
  - OrderDO → OrderRecordDO：一对多（一个用户一个商品一个日期对应一条记录）
关联其他聚合：
  - 引用「商品」聚合中的 GoodsDO 和 GoodsProductDO（通过 goodsId 和 productId）
  - 引用「优惠券」聚合中的 CouponDO（通过 couponId）
  - 引用「用户」聚合中的 UserDO（通过 userId）
证据：core/DO/mall/OrderDO.java, core/DO/mall/OrderGoodsDO.java, core/DO/mall/OrderRecordDO.java
适用范围：仅适用于已提交的订单，购物车中的商品和未下单的预订不在此聚合内
标签：订单、商品、交易
```

### 提取方式

1. **AST 提取实体关联**
   - 扫描实体类（DO/Entity/Model）中的外键字段（命名包含 Id、FK、Ref 等后缀的字段）
   - 扫描实体类中的关联字段（List<OtherEntity>、@OneToMany 等注解）
   - 扫描 Mapper XML 中的 JOIN 语句和关联查询
   - 扫描实体类中引用其他实体 ID 的字段

2. **AST 识别聚合边界**
   - 识别"一对多"关系中的"一"方作为聚合根
   - 被"一对多"引用的实体归入该聚合
   - 通过 Service 的事务边界辅助判断聚合边界（同一事务中操作的实体通常属于同一聚合）

3. **LLM 生成**
   - 从提取的实体关联中，LLM 生成聚合名称和聚合描述
   - LLM 为每个聚合总结核心实体和实体关系
   - LLM 识别跨聚合引用关系

### 生成约束

- 只记录核心业务实体（DO/Entity/Model）之间的关系，不记录 DTO、VO 等传输类
- 聚合边界的判断必须有代码证据支撑（外键字段或事务边界）
- 实体关系描述应说明关联字段，使 Agent 能直接定位到代码中的关联定义
- 传输类（DTO、VO）与业务实体之间的映射关系不记录，Agent 可自行查看 Transfer/Converter 类

## 8. 跨域业务流程知识

### 定义

跨域业务流程知识记录跨越多个能力域的端到端业务路径。它回答"一个完整的业务目标如何经过多个域协作完成"。

跨域业务流程的价值在于提供**全链路视角**。能力目录按域拆分，能力关系记录点对点关系，但 Agent 理解一个完整的业务场景（如"用户下单支付全流程"）时，需要从多个域的知识中自行拼凑路径。跨域业务流程直接提供这条拼凑后的路径，是信息增量最高的知识类型之一。

跨域业务流程只记录涉及至少 2 个能力域的流程，且流程不能从能力关系知识中简单推导。如果一个流程完全在一个域内完成，或只是能力关系中已记录的两域调用链，不需要重复记录。

### 结构

一条跨域业务流程知识包含：

- 流程名称：业务化的流程名称（如"商品购买全流程"、"学生入学到首次上课流程"）
- 业务目标：该流程要达成的业务目标
- 涉及域（有序）：流程经过的能力域列表，按执行顺序排列
- 流程步骤：每个步骤的操作、所在域和关键约束/分支
- 触发条件：流程的触发入口（如用户操作、定时任务、外部回调）
- 完成标志：流程正常结束的标志
- 关键分支（可选）：流程中的主要分支点或异常处理路径
- 适用范围：该流程适用的业务场景
- 标签：用于分类和检索的关键词（1~3 个）
- 证据：流程各步骤涉及的关键代码位置

### 产物示例

```
## 商品购买全流程

流程名称：商品购买全流程
业务目标：用户从浏览商品到完成支付的完整购买路径
涉及域（有序）：商品浏览 → 购物车 → 订单管理 → 支付
触发条件：用户点击"购买"按钮
完成标志：支付回调确认，订单状态变更为"已支付"（201）
流程步骤：
  1. 浏览商品（商品浏览域）：用户查看商品列表和详情，选择规格
  2. 加入购物车（购物车域）：将商品添加到购物车，可调整数量
  3. 提交订单（订单管理域）：从购物车结算，校验库存、优惠券，创建订单（状态 101-待支付）
  4. 发起支付（订单管理域）：选择支付渠道（支付宝/微信/余额），调用对应 SDK 创建支付单
  5. 支付回调（订单管理域）：接收支付平台回调，乐观锁更新订单状态为 201-已支付
关键分支：
  - 余额支付：跳过外部支付平台，直接扣减余额并更新状态
  - 超时未支付：Quartz 定时任务（OrderUnpaidJob）自动取消订单（状态 401），回滚库存和优惠券
适用范围：仅适用于正常的商品购买路径，退款和售后有独立流程（当前未实现）
标签：购买、订单、支付、全流程
证据：GoodsController, CartController.checkout, OrderController.submit/appPay/payCallback, OrderUnpaidJob
```

### 提取方式

1. **基于能力关系构建路径**
   - 从已有的能力关系知识出发，识别跨域调用链
   - 从外部触发入口（Controller 方法、定时任务、回调入口）开始追踪完整路径
   - 路径追踪深度限制为 3~4 层跨域调用

2. **识别端到端流程**
   - 一个端到端流程从一个外部触发开始，到一个业务目标完成（或进入等待外部事件的状态）结束
   - 从能力目录的操作列表和访问方式中识别触发入口
   - 从约束知识和概念知识中获取流程中的关键分支和状态变化

3. **过滤**
   - 排除仅涉及单个域的流程（属于能力目录的域级上下文，不在此记录）
   - 排除能从能力关系知识中直接推导的流程（如"A 调用 B"已记录在能力关系中，不需要重复为跨域流程）
   - 保留涉及 2 个以上域、且有分支或状态变化的复杂流程

4. **LLM 生成**
   - 从过滤后的流程路径中，LLM 生成流程名称、业务目标和关键分支描述
   - 步骤描述应简洁，重点标注分支点和约束条件

### 生成约束

- 流程步骤中的能力域名称必须与能力目录中的域名称一致
- 关键分支描述必须有代码证据支撑，不推断未实现的分支
- 跨域业务流程是最高价值的知识类型，条目数量应少而精（典型项目 3~8 条），只记录核心的端到端业务路径
