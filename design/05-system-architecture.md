# 系统架构设计

本文定义 `ai-wiki` 的系统架构决策，包括系统模式选择、LLM 交互方式、大上下文处理策略和程序侧工具能力。

本文是流程层（04）的延伸。04 定义生成流程"做什么"，本文定义"用什么方式做"。

## 系统架构模式

### 选择：管线编排 + 程序侧工具

`ai-wiki` 采用管线编排架构，程序控制流程编排和上下文组装，LLM 仅在生成环节作为生成器参与。

不采用 Agent 自主探索架构（LLM 通过工具调用自主决定读哪些文件、查什么 AST），原因：

- **上下文组装需要完整性保证**。文件扫描、AST 解析、候选提取和分组策略由程序规则覆盖，能保证不遗漏文件。Agent 模式下的 LLM 探索路径不可预测，可能遗漏关键文件。
- **成本必须可控**。管线模式下 LLM 调用次数 = 分组数量，可提前预算。Agent 模式下每个分组可能触发多次工具调用，大型仓库的成本不可预测。
- **增量更新要求确定性**。程序需要精确维护"文件变更 → 受影响知识条目"的映射关系。这个映射用程序规则维护比让 LLM 自行判断更可靠。
- **可复现性**。相同输入在管线模式下产出一致，Agent 模式下 LLM 的工具调用决策不可复现。

### 系统层次

```
┌─────────────────────────────────────────────┐
│  编排层：流程调度、分组决策、生成阶段管理      │
├─────────────────────────────────────────────┤
│  工具层：文件扫描、AST 解析、AST 查询、配置解析 │
├─────────────────────────────────────────────┤
│  交互层：上下文组装、LLM 调用、JSON 解析校验    │
├─────────────────────────────────────────────┤
│  产物层：JSON → Markdown 转换、索引生成、落盘   │
└─────────────────────────────────────────────┘
```

- 编排层负责步骤调度和流程控制，对应 04 定义的 6 个步骤
- 工具层提供代码分析能力，全部由程序实现，不涉及 LLM
- 交互层管理 LLM 调用的输入组装和输出解析
- 产物层负责格式转换和文件写入

### LLM 角色边界

LLM 在系统中的角色是**生成器**：接收程序预组装的上下文，输出符合 Schema 的结构化知识条目。

LLM 不参与以下决策：

- 不参与上下文组装决策（读哪些文件、查什么 AST 由程序决定）
- 不参与分组决策（分组策略由程序规则执行）
- 不参与筛选决策（候选过滤由程序规则执行）
- 不参与校验决策（结构化校验由程序规则执行，内容质量评估时 LLM 作为辅助）
- 不参与格式转换（JSON → Markdown 由程序模板引擎执行）

## LLM 交互格式

### 上下文组装

每次 LLM 调用的输入由程序侧完成组装，包含以下部分：

| 组成部分 | 说明 | 是否必须 |
|---------|------|---------|
| 知识类型 Schema | 该类型的 JSON Schema 定义和字段说明，使 LLM 知道输出格式 | 必须 |
| 候选信息 | 该分组内的候选列表，包含代码片段、位置和上下文 | 必须 |
| 生成指令 | 指导 LLM 如何从候选信息生成知识条目的指令 | 必须 |
| 已有名称 | 生成阶段 1 已生成的能力域名称和概念名称 | 生成阶段 2+ |
| 已有标签池 | 现有 `_index.md` 中的标签列表 | 增量更新时 |
| 产物示例 | 该类型的少量产物示例，帮助 LLM 理解输出风格 | 必须 |

上下文组装的总 token 量应适配目标模型的上下文窗口，具体预算策略见下文"实现挑战与应对"。

### JSON 结构化输出

LLM 输出 JSON 格式的结构化数据，不直接输出 Markdown。

选择 JSON 结构化输出而非直接输出 Markdown，原因：

- **可校验**：程序可对 JSON 字段做精确校验（必填字段、标签数量、枚举值），Markdown 格式的字段提取依赖正则匹配，极其脆弱
- **可编程**：增量更新时程序可精确修改单个字段（如只更新"生成时间"），不需要重新生成整个 Markdown
- **格式一致性**：Markdown 的格式一致性由程序模板引擎保证，不依赖 LLM 对 Markdown 格式的遵循度
- **跨类型引用修正**：校验发现引用路径错误时，程序可直接在 JSON 层面修正字段值

不选择 Markdown 直接输出的核心原因：04 定义的 5 个校验维度中，结构完整性、证据有效性和跨类型引用一致性都需要对字段做精确提取。Markdown 格式下无法可靠地完成这些校验。

### JSON Schema 设计原则

为每种知识类型定义独立的 JSON Schema，遵循以下原则：

**扁平化**：所有知识类型的 JSON 最多两层嵌套，禁止深层嵌套对象。嵌套越深，LLM 输出格式错误的概率越高。

**数组元素结构统一**：数组内的元素结构相同，不混合不同类型。

**字段类型约束**：每个字段有明确的类型（string/number/array/boolean）和长度约束（如"不超过 100 字符"）。

**必填与可选分离**：Schema 中明确标注必填字段和可选字段。可选字段在信息不足时设为 null 或空数组，不编造内容。

### JSON Schema 示例

以能力目录为例：

```json
{
  "name": "订单管理",
  "description": "商品购买的订单全生命周期管理",
  "businessContext": "支持支付宝、微信和余额三种支付渠道，支付回调与定时任务存在竞态条件，使用乐观锁保护状态更新",
  "scope": "仅适用于实物商品和虚拟商品的购买订单",
  "entryClass": "OrderController",
  "tags": ["订单", "交易", "购买"],
  "operations": [
    {
      "name": "创建订单",
      "method": "POST /order/submit",
      "location": "OrderController.submit()",
      "description": "提交商品购买订单，完成商品校验、库存扣减和优惠券核销",
      "tags": ["订单", "创建", "购买"],
      "roleRequirements": ["学生", "教师"],
      "keyConstraints": ["库存充足", "优惠券有效"]
    },
    {
      "name": "取消订单",
      "method": "POST /order/cancel",
      "location": "OrderController.cancel()",
      "description": "取消未发货订单，回滚库存和优惠券",
      "tags": ["订单", "取消", "库存"],
      "roleRequirements": ["学生", "教师"],
      "keyConstraints": ["订单状态为待支付（101）"]
    }
  ],
  "statusFlow": ["101-待支付", "201-已支付", "301-已发货", "302-已确认", "401-已取消", "402-已过期"],
  "sourceFiles": ["src/controller/OrderController.java"]
}
```

**可选字段说明**：

- `businessContext`：域级业务上下文，从操作列表和代码结构综合提炼
- `statusFlow`：该域核心实体的状态流转序列，仅当该域涉及状态机时填写
- `keyConstraints`：操作级的关键约束摘要（1~2 条），仅当操作有重要前置条件时填写
- `roleRequirements`：操作级的角色要求列表，仅当操作有权限注解或角色判断时填写

这些字段为可选，不满足填写条件时省略。程序在 JSON 校验时对可选字段不做必填检查。

其他知识类型的 Schema 结构类似，只是字段不同。Schema 定义从 02 中各类型的结构定义直接派生。

### JSON 校验流程

程序对 LLM 输出的 JSON 执行以下校验：

```
LLM 输出文本 → 提取 JSON → Schema 校验 → 业务校验 → 通过 / 失败
```

**Schema 校验**：必填字段是否存在、字段类型是否正确、标签数量是否在 1~3 范围、枚举值是否合法。

**业务校验**：证据路径是否存在于仓库中、证据路径是否出现在生成输入中（防止 LLM 编造路径）、跨类型引用的目标名称是否存在。

校验通过的 JSON 进入 Markdown 转换环节。校验失败的处理见"错误恢复"。

### JSON → Markdown 转换

转换层是纯模板引擎，不涉及 LLM 调用：

- 每种知识类型对应一个 Markdown 模板
- 模板从 03 定义的详情文件结构和 02 定义的产物示例派生
- 转换过程：JSON 字段填充到 Markdown 模板 → 生成头部元信息（类型、生成时间、来源文件、标签） → 生成正文内容 → 写入文件

转换是确定性的：相同 JSON 输入产出相同 Markdown 输出。

## 大上下文处理

### 问题描述

04 的分组策略对齐代码的物理边界（Controller、包、模块）。但物理边界不等于上下文边界——一个 Controller 可能有 50 个方法，一个 Service 包可能有 40 个类，代码量可能超出单次 LLM 上下文窗口。

知识的完整性要求看到全貌，但上下文窗口只能容纳局部。

### 解决策略：三层递进

三层策略按成本递增触发，每一层解决不同程度的上下文溢出。

#### 第一层：上下文分层

**核心思路**：不是所有代码都需要完整源码。不同知识类型对代码细节的需求层次不同。

定义两个表示层级：

| 表示层级 | 内容 | 每方法约 token 量 | 适用场景 |
|---------|------|-----------------|---------|
| 结构概要 | 方法名 + 注解 + 参数类型 + 返回类型 | ~10 | 能力目录的方法清单、能力关系的调用链 |
| 完整源码 | 方法体全文 | ~200-500 | 概念知识（需要理解业务逻辑）、复杂约束 |

**两阶段上下文组装流程**：

```
第一轮：程序把分组内所有代码元素转为"结构概要"
       → 连同提示词和 Schema 发给 LLM
       → LLM 输出：知识条目骨架 + 需要展开源码的元素清单

第二轮：程序只加载 LLM 指定的元素的完整源码
       → 发给 LLM
       → LLM 输出：补全描述、证据、引用等详细字段
```

这一层能解决大多数溢出问题，因为大多数知识条目的骨架可以从高层表示确定，只有描述和证据需要源码细节。

能力目录通常只需第一轮（方法签名足够生成操作列表），概念知识通常需要两轮（需要理解业务逻辑才能生成准确描述）。

#### 第二层：分组拆分 + 结果合并

**触发条件**：结构概要也超出上下文窗口时（如 200 方法的 Controller、100 个类的包），触发第二层。

**拆分策略**：拆分切割点必须在代码的语义边界上，保证相关知识元素在同一个子组中：

| 知识类型 | 二级拆分切割点 | 理由 |
|---------|-------------|------|
| 能力目录 | 按 URL 前缀或方法名前缀分组 | 相关操作应在一起，LLM 才能生成一致的命名 |
| 概念知识 | 按子包或类名前缀分组 | 同名前缀的类往往属于同一业务概念 |
| 约束知识 | 按 Service 类或业务方法分组 | 同一 Service 的约束有业务关联 |
| 能力关系 | 按入口方法分组，追踪 2-3 层 | 保证调用链完整性 |
| 数据模型 | 按实体关联图拆分 | 外键关联的实体应保持在一起 |

**合并策略**：拆分后的子组独立调用 LLM 生成子结果，然后合并。

合并分两种方式：

**程序合并**（适用于生成阶段 1 的知识类型）：
- 能力目录：多个子组的操作列表直接拼接为一个域文件
- 概念知识：子组产出的概念条目直接追加，程序按名称去重
- 数据模型：子组产出的实体和关系直接追加

**LLM 辅助合并**（适用于生成阶段 2 中语义可能重叠的知识类型）：
- 约束知识：不同子组可能产生语义重叠的约束，需要 LLM 判断合并或保留
- 能力关系：子组间的调用链可能交叉，需要 LLM 连接跨子组的关系

LLM 辅助合并的输入是子组产出的知识条目文本（已压缩后的结果，不是原始代码），token 量远小于原始代码。

```
大分组 → 按语义边界拆为 N 个子组
       → 每个子组独立生成子结果
       → 阶段 1 子结果：程序合并（拼接 + 去重）
       → 阶段 2 子结果：LLM 合并（输入是子结果文本，不是原始代码）
       → 产出最终知识条目
```

#### 第三层：多轮精炼

**触发条件**：拆分 + 合并后，跨子组可能出现不一致（命名冲突、描述矛盾、遗漏关联）时触发。

**精炼流程**：

```
合并后的知识条目（草稿）
  → 发给 LLM 做一致性审查
  → 输入：草稿全文 + 审查指令（"检查命名一致性、描述重复、跨操作引用完整性"）
  → 输出：修正后的最终知识条目
```

精炼轮的输入是知识条目文本（不是原始代码），token 量可控。精炼通常只需一轮，不反复迭代。

#### 三层策略触发条件

```
分组代码量评估：

代码量 ≤ 上下文窗口 70%？
  → 直接单次 LLM 调用

代码量 > 70%，但结构概要 ≤ 70%？
  → 第一层：上下文分层（两阶段上下文组装）

结构概要也 > 70%？
  → 第二层：分组拆分 + 结果合并

合并后出现跨子组不一致？
  → 第三层：多轮精炼
```

## 程序侧工具能力

程序侧需要实现以下工具能力，全部由程序代码实现，不涉及 LLM 调用。

### 文件扫描工具

- 识别目标仓库中与知识提取相关的文件
- 输出文件清单（路径、类型、大小）
- 支持 04 定义的文件类型识别和排除规则
- 解析 `.gitignore` 辅助排除判断

### AST 解析工具

- 从源代码文件中提取结构化信息（类、方法、字段、导入、包结构）
- 支持主流语言的解析（Java、TypeScript、Go、Python、Kotlin）
- 处理语言特有结构（注解/装饰器、泛型、嵌套类、接口默认方法等）

### AST 查询工具

- 按注解/装饰器查找类和方法
- 按类名查找方法、字段和继承关系
- 追踪方法调用链（调用方和被调用方）
- 获取方法的源代码片段
- 查找引用某个实体类的所有位置

### 配置文件解析工具

- 解析 `.yml`、`.yaml`、`.properties`、`.json`、`.toml`、`.env` 等格式
- 输出结构化键值对，支持嵌套结构和变量引用解析
- 支持配置项的键名查询和值查询

### 文档提取工具

- 从 `.md`、`.txt`、`README*` 和 API 文档文件中提取纯文本内容
- 提取的文本内容按文件组织，在 LLM 调用时根据相关性注入上下文
- 处理大文档的截断策略（单文档超过阈值时按段落截取关键部分）

### 调用图构建工具

- 基于 AST 查询结果构建方法级调用图
- 支持静态调用和接口-实现追踪
- 标注无法静态追踪的调用类型（反射、动态代理、事件机制）

## 多模块项目处理

实际项目往往不是单模块结构，而是由多个子模块组成。根据 04 步骤 3.5 的分析单元划分结果，多模块项目分为两种处理模式。

### 紧耦合模式

当多个模块构成"一个系统的多个部分"时（共享核心实体、存在跨模块调用、共用数据库），整个仓库作为一个分析单元，生成一份知识库。

#### 处理策略

```
扫描构建配置（pom.xml / build.gradle / package.json）
  → 识别所有子模块及其依赖关系
  → 分类模块角色（deployable vs shared）
  → 共享模块源码直接解析，纳入统一 AST 图谱
  → 生成 modules.json 记录模块拓扑
  → 知识条目中标注模块归属
```

#### 与单模块项目的区别

| 维度 | 单模块项目 | 紧耦合多模块 |
|------|-----------|------------|
| AST 图谱 | 解析 src/ 下所有源码 | 解析所有模块的源码，共享模块不视为外部 |
| 模块标注 | 不需要 | 每条知识标注所属模块 |
| 架构概览 | 单服务架构描述 | 多模块架构描述 + 模块拓扑 |
| 分组策略 | 按 Controller/包分组 | 按模块内的 Controller/包分组 |
| 增量更新 | 文件变更 → 知识条目 | 文件变更 → 模块维度 → 知识条目 |

#### 对知识生成的影响

| 知识类型 | 影响 | 处理方式 |
|---------|------|---------|
| 能力目录 | 入口分散在多个 deployable 模块 | 按模块内 Controller 分组，标注所属模块 |
| 概念知识 | 实体类可能定义在共享模块 | 标注定义模块（如 mall-mbg）和使用模块（如 mall-admin、mall-portal） |
| 数据模型 | 聚合中的实体可能来自共享模块 | 标注实体所属模块，聚合边界仍按外键判断 |
| 约束知识 | 约束逻辑可能跨模块 | 标注约束生效的模块 |
| 能力关系 | 调用链可能穿过模块边界 | 标注关系是否跨模块，跨模块调用置信度标注 |
| 跨域业务流程 | 流程可能涉及多个模块 | 标注涉及的模块列表 |

### 松耦合模式

当多个模块是"多个独立系统碰巧放在同一仓库"时（各自独立数据库、无直接代码调用、独立部署），每个可部署服务作为独立分析单元。

#### 处理策略

```
扫描构建配置
  → 识别各可部署服务
  → 每个服务独立执行步骤 4~7
  → 各服务目录下生成独立 ai-knowledge/
  → 共享模块按外部模块处理
```

#### 外部模块处理

在松耦合模式下，每个分析单元视其他模块为外部模块。主模块的代码引用其他模块中定义的实体类、接口和工具类，AST 图谱无法直接解析这些外部符号：

- **外部模块识别**：扫描构建配置（pom.xml、build.gradle 等），识别项目依赖的内部模块（如 music-core、common-service）
- **外部模块源码解析**：如果外部模块的源码在本地可访问（如 Maven 本地仓库中的 sources.jar，或 monorepo 中的兄弟目录），一并解析其源码纳入 AST 图谱
- **外部模块符号标注**：当外部模块源码不可访问时，从 import 语句推断外部类的全限定名，在 AST 图谱中标注为"外部模块符号"（仅有名称和所属模块，无字段和方法详情）
- **影响范围**：外部模块符号主要影响概念知识和数据模型的提取——当实体类定义在外部模块时，证据中标注所属模块，概念知识的"代码体现"字段标注外部来源

#### 对知识生成的影响

| 知识类型 | 影响 | 处理方式 |
|---------|------|---------|
| 能力目录 | 通常不受影响（入口定义在主模块） | 正常生成 |
| 概念知识 | 实体类可能定义在外部模块 | 证据标注模块归属，概念仍从使用侧提取 |
| 数据模型 | 聚合中的实体可能跨模块 | 标注各实体所属模块，聚合边界仍按外键判断 |
| 约束知识 | 约束检查可能调用外部模块方法 | 正常生成，证据指向调用侧 |
| 能力关系 | 调用链可能穿过模块边界 | 跨模块调用标注为"推断"（confidence < 1.0） |

## 错误恢复

### 分层错误处理

| 错误类型 | 处理方式 | 最大重试次数 |
|---------|---------|------------|
| LLM 调用失败（网络/超时/限流） | 指数退避重试 | 3 次 |
| JSON 解析失败（非法 JSON） | 提取修复 → 重试 | 1 次 |
| JSON 校验失败（缺字段/格式错） | 按问题类型分别处理（见下） | 1 次 |
| 内容质量不达标 | 重新生成并强化质量指令 | 1 次 |
| 合并冲突 | 程序自动去重 / LLM 辅助判断 | 不重试 |

### JSON 校验失败的细分处理

| 校验问题 | 处理方式 |
|---------|---------|
| 缺必填字段 | 补充缺失字段提示后重试 |
| 标签超量 | 程序截断为 3 个，不重试 |
| 证据路径无效 | 程序移除无效路径，不重试 |
| LLM 编造路径（路径不在生成输入中） | 丢弃该条目，记录到生成报告 |
| 跨类型引用名称不匹配 | 程序用实际名称修正引用 |

### 部分失败隔离

- 某个分组生成失败不影响其他分组的生成和校验
- 生成阶段 1 的失败分组名称不注入到生成阶段 2 的上下文中
- 最终生成报告列出成功和失败的分组

## 标签系统实现

标签在两个层级生成，与 02 和 03 的定义对应：

| 层级 | 生成位置 | 使用位置 | 示例 |
|------|---------|---------|------|
| 域级标签 | 能力目录的 JSON 顶层 `tags` 字段 | `_index.md` 的标签列 | "订单、交易、购买" |
| 条目级标签 | 各知识类型 JSON 的 `tags` 字段 | 各 `_index.md` 的标签列和详情文件头部 | "师徒、绑定、频率限制" |

标签一致性由程序保证：
- 增量更新时，程序读取现有 `_index.md` 提取已有标签池，注入 LLM 生成上下文
- 校验阶段，程序检查新标签是否与已有标签语义重复，重复时替换为已有标签
- 标签最短形式优先（如"订单"而非"订单管理"），由生成指令约束

## 实现挑战与应对

以下列出真实实现中可能遇到的非平凡问题及应对方案。

### 挑战 1：JSON 输出的实际不稳定性

**问题**：即使 Schema 扁平化，LLM 仍可能产出非法 JSON。常见情况包括：尾部多余逗号、键名未加引号、字符串内未转义换行符、在 JSON 前后添加解释性文本、数组元素结构不一致。

**应对**：

- **解析前清洗**：用正则提取 ```json ... ``` 代码块内容，丢弃 JSON 前后的解释性文本
- **宽松解析器**：先用标准 JSON 解析，失败后降级到宽松解析器（容忍尾部逗号、未加引号的键名）
- **API 特性利用**：部分 LLM API 支持 JSON mode 或 structured output 参数，强制输出合法 JSON
- **Few-shot 示例**：提示词中嵌入 1~2 个完整的 JSON 输出示例，锚定 LLM 的输出格式
- **温度控制**：JSON 生成时使用低温度（0~0.2），降低格式变异概率

### 挑战 2：Token 预算分配

**问题**：每次 LLM 调用的上下文窗口需要在 Schema、提示词、示例、候选代码和输出预留之间分配。代码量容易挤占其他部分。

**应对**：

定义 token 预算分配比例：

| 组成 | 预算比例 | 说明 |
|------|---------|------|
| Schema 定义 | ~8% | JSON Schema + 字段说明 |
| 生成指令 | ~8% | 提取规则和生成约束 |
| 产物示例 | ~8% | 1~2 个完整示例 |
| 候选代码 | ~50% | 代码片段、位置、上下文 |
| 已有名称/标签池 | ~5% | 生成阶段 2+ 和增量更新时 |
| 输出预留 | ~21% | 为 JSON 输出预留空间 |

候选代码占比 50% 是基于试生成经验的调整——复杂域（如包含 16 个方法和 3 种支付渠道回调的 OrderController）需要充足的代码空间，否则上下文分层被迫触发更多轮次。

程序在组装上下文时计算各部分的 token 量。当候选代码超出 50% 预算时，触发上下文分层或分组拆分，而不是压缩其他部分。对于代码量特别大的域，可临时将候选代码比例上调至 55%，相应压缩产物示例（保留 1 个示例而非 2 个）。

Token 计算使用目标模型的 tokenizer。不同模型的 tokenizer 不同，程序应支持配置目标模型并加载对应 tokenizer。

### 挑战 3：多语言 AST 解析一致性

**问题**：不同语言的 AST 结构差异大。Java 的注解（`@RequestMapping`）、TypeScript 的装饰器（`@Controller`）、Go 的 struct tag、Python 的装饰器（`@app.route`）语法完全不同，但需要映射到统一的 AST 图谱模型。

**应对**：

- **统一 AST 模型**：定义语言无关的 AST 数据结构（ClassInfo、MethodInfo、FieldInfo、AnnotationInfo），每种语言实现各自的适配器
- **优先覆盖主流语言**：先实现 Java（tree-sitter-java 或 JavaParser）和 TypeScript（tree-sitter-typescript 或 TypeScript Compiler API），其他语言渐进添加
- **语言检测**：从文件扩展名和构建配置（`pom.xml` → Java、`package.json` → TypeScript）自动识别语言
- **注解/装饰器抽象**：不同语言的注解语法不同，但在 AST 模型中统一为 AnnotationInfo（名称 + 参数键值对），屏蔽语法差异

### 挑战 4：调用链追踪的静态分析盲区

**问题**：静态 AST 分析无法追踪以下调用类型：反射调用、动态代理、事件发布/订阅机制、策略模式和工厂模式下的动态分派、通过配置决定的路由。

**应对**：

- **盲区标注机制**：调用图中无法静态追踪的边标注为"推断"（confidence < 1.0），LLM 在生成能力关系时能看到哪些调用链是确定的、哪些是推断的
- **辅助启发式**：对常见模式做启发式追踪——如 Spring 的 `@EventListener` 注解可以静态关联发布者和监听者、接口-实现关系可以通过 `implements` 关键字追踪
- **盲区声明注入 LLM 上下文**：提示词中明确告知 LLM "以下调用关系无法通过静态分析确认：[列表]"，让 LLM 在生成时标注不确定性

### 挑战 5：配置文件变量解析

**问题**：Spring 等框架的配置值经常通过 `${placeholder}` 引用或 `@Value("${key}")` 注入，实际值可能在另一个配置文件中定义，或依赖运行时环境变量。

**应对**：

- **配置文件索引**：解析所有配置文件，建立键值对映射表
- **变量解析**：尝试解析 `${}` 引用，从同仓库的其他配置文件中查找定义
- **未解析标记**：无法在仓库内解析的变量标记为"未解析"，LLM 生成边界知识时能看到配置键名和原始表达式
- **环境变量识别**：识别常见环境变量引用模式（`System.getenv()`、`process.env.*`），记录为外部依赖

### 挑战 6：上下文分层中的展开决策

**问题**：第一层策略中，LLM 需要从方法签名判断哪些方法需要展开完整源码。方法签名信息可能不足以做出准确判断——LLM 可能要求展开过多方法（浪费上下文）或过少方法（遗漏关键细节）。

**应对**：

- **程序预选**：程序基于启发式规则预选必须展开的方法——如包含复杂业务注解（`@Transactional`、自定义业务注解）、方法体行数超过阈值、方法名包含核心业务动词
- **LLM 判断上限**：提示词中限制 LLM 最多额外请求展开 N 个方法（如 5 个），防止全量展开
- **判断标准注入**：提示词中给出明确的判断标准——"如果从方法名和注解无法判断业务含义，则请求展开源码"
- **二轮溢出处理**：如果第二轮展开后仍超出上下文，对超出部分做截断并标注"部分源码已截断"，LLM 基于可用信息生成，质量不达标时丢弃
- **经验积累**：随着运行次数增加，程序可统计"哪些类型的方法签名通常需要展开"，优化预选规则

### 挑战 7：知识条目粒度控制

**问题**：LLM 生成的约束知识粒度可能不一致——有时过细（每个 if 判断都是一条约束），有时过粗（所有订单约束合并为一条）。

**应对**：

- **粒度标准嵌入指令**：生成指令中明确定义——"一条约束知识对应一个独立的业务规则，该规则可被单独引用和单独违反"
- **正反例**：提示词中提供正确粒度和错误粒度的示例
- **后处理合并/拆分**：
  - 过细条目：程序检测同一来源文件产出的多条短约束，合并为一条
  - 过粗条目：程序检测描述中包含多个独立规则关键词（"且"、"同时"、"另外"），标记为可能需要拆分

### 挑战 8：证据路径编造防御

**问题**：LLM 可能编造看似合理但实际不存在的文件路径作为证据。

**应对**：

- **白名单校验**：所有证据路径必须出现在该分组的生成输入中（输入中的文件路径列表是白名单），不在白名单中的路径一律移除
- **路径存在性校验**：校验路径对应的文件是否实际存在于仓库中
- **生成指令约束**：明确告知 LLM "只能使用输入中提供的文件路径作为证据，不得编造路径"

### 挑战 9：大文档上下文注入

**问题**：仓库中可能包含大型文档（如 50 页的 API 文档），全量注入 LLM 上下文会挤占代码空间。

**应对**：

- **分段索引**：大文档按段落或章节分段，建立段落级索引
- **相关性匹配**：根据当前分组的业务领域（包名、类名前缀），用关键词匹配筛选相关段落
- **摘要降级**：超大文档先提取目录和章节标题作为概要，LLM 按需请求展开具体章节
- **截断阈值**：单个文档注入上下文的文本量设置上限（如 2000 token），超出时只注入相关段落

### 挑战 10：增量更新与全量生成的一致性

**问题**：增量更新只重新生成受影响的条目，但使用相同 Schema 和提示词时，LLM 的输出风格可能因输入上下文不同而产生差异（如命名风格、描述长度）。

**应对**：

- **上下文对齐**：增量更新时，除了注入受影响分组的候选信息，还注入相邻分组的知识条目概要，使 LLM 有全局上下文参考
- **标签池注入**：始终注入现有标签池，保证标签一致
- **已有名称注入**：始终注入现有能力域名称和概念名称，保证引用一致
- **风格示例**：从现有知识库中选取 1~2 个高质量条目作为 few-shot 示例注入

### 挑战 11：生成阶段间的级联失败

**问题**：生成阶段 1 的某个分组失败，导致该能力域名称不存在。生成阶段 2 中引用该能力域的约束知识、能力关系知识将无法生成正确的引用。

**应对**：

- **失败传播隔离**：生成阶段 1 的失败分组名称不注入到阶段 2 的名称列表中
- **阶段 2 引用降级**：当阶段 2 的 LLM 输出引用了一个不存在的名称时，程序移除该引用并在知识条目中标注"引用待补全"
- **重试补全**：如果阶段 1 的失败分组在重试后成功，程序触发受影响阶段 2 条目的重新生成

### 挑战 12：Markdown 转换的边界情况

**问题**：JSON → Markdown 转换虽然是确定性的，但需要处理特殊字符（管道符 `|` 破坏表格格式）、长文本（描述过长导致表格行过宽）和空值（可选字段为 null）。

**应对**：

- **特殊字符转义**：对表格单元格内的 `|` 转义为 `\|`
- **长文本截断**：表格内的描述超过阈值时截断并添加省略号，完整描述放在正文中
- **空值处理**：可选字段为 null 时，表格中显示为 `—` 或省略该列
- **模板测试**：转换层是纯代码，应做到完整的单元测试覆盖，用各种边界 JSON 输入测试转换输出

### 挑战 13：LLM 输出 Token 上限

**问题**：LLM 的输出 token 上限通常远小于输入上限（如输入 200k token，输出上限 8k~32k token）。一个 50 方法的 Controller 生成的能力目录 JSON 可能轻松超过 8k token，导致输出被截断、JSON 不完整、解析失败。

**应对**：

- **输出长度预估**：程序在调用前根据候选数量预估输出 token 量（如每个操作约 150~250 token）。当预估超过目标模型的输出上限时，触发分组拆分——不是因为输入放不下，而是因为输出放不下
- **输出上限可配置**：不同模型的输出上限差异大，程序需要可配置。建议默认按 8k 输出预算设计，大输出模型（32k+）作为优化选项
- **分段输出**：极端情况下，可以让 LLM 分批输出（如"先输出前 25 个操作，下一轮给出后 25 个"）。但这增加了调用次数和复杂度，仅作为兜底方案
- **上下文分层联动**：输出预估与"大上下文处理"的三层策略联动——当输出预估超过上限时，即使输入上下文充裕，也触发分组拆分

### 挑战 14：批处理调度与 API 限流

**问题**：大型仓库可能产生数百个 LLM 调用。生成阶段 1 中各分组可并行，但 API 有并发限制和每分钟 token 限制。无调度的并行发送会触发限流，导致大量请求被拒绝。

**应对**：

- **令牌桶调度器**：实现令牌桶算法控制并发，按 API 限流参数配置桶容量和补充速率
- **优先级队列**：生成阶段 1 的调用优先级高于阶段 2（阶段 2 依赖阶段 1 产出），同阶段内按分组大小排序（大分组优先，因为耗时更长）
- **进度追踪**：实时显示已完成/总数/失败数，支持断点续跑（已成功的分组不重复调用）
- **断点续跑持久化**：将已完成分组的结果持久化到临时文件，进程中断后重启时跳过已完成的分组

### 挑战 15：幂等性与生成稳定性

**问题**：相同输入运行两次，LLM 的输出可能不同（温度 > 0 时）。增量更新时，重新生成的条目风格可能与未变更条目不一致。CI/CD 中两次构建的知识库可能不同，调试时无法复现某次生成的具体结果。

**应对**：

- **温度设为 0**：JSON 生成环节使用 temperature=0，最大程度保证确定性
- **随机种子**：部分 API 支持 seed 参数，设置固定种子进一步保证一致性
- **生成参数记录**：在 `.meta` 文件中记录每次生成的模型名称、温度、seed 等参数，便于复现
- **接受有限非确定性**：内容质量评估和精炼轮可以使用稍高温度（0.3~0.5），因为这些环节需要 LLM 的判断力。最终产物仍由 JSON 校验把关

### 挑战 16：AST 解析器的选择与维护

**问题**：AST 解析是整个系统的基石，但不同语言的解析器成熟度差异大。选择错误的解析器会导致后期维护困难。

**各语言解析器现状**：

| 语言 | 可选解析器 | 成熟度 | 主要问题 |
|------|-----------|-------|---------|
| Java | JavaParser / tree-sitter-java | 高 | JavaParser 功能完整但重，tree-sitter 轻量但需自建语义层 |
| TypeScript | TypeScript Compiler API / tree-sitter-typescript | 高 | Compiler API 可获取类型信息但启动慢 |
| Go | go/ast（标准库） | 高 | 标准库完整，但需理解 Go AST 结构 |
| Python | ast（标准库）/ tree-sitter-python | 中 | 标准库 AST 缺少装饰器参数解析 |
| Kotlin | tree-sitter-kotlin / Kotlin Compiler | 低 | 缺少成熟的独立解析器 |

**应对**：

- **统一用 tree-sitter**：tree-sitter 支持所有目标语言，API 一致，解析速度快（增量解析），适合大规模代码库。代价是需要自建语义层（tree-sitter 返回 CST，需转换为业务 AST 模型）
- **渐进式语言支持**：V1 只支持 Java + TypeScript，覆盖最常见的企业级和前端仓库。Go/Python/Kotlin 在后续版本添加
- **语言适配器模式**：每种语言实现一个 `LanguageAdapter` 接口（`parse(file) → UnifiedAST`），新语言只需实现适配器
- **解析失败容错**：单个文件解析失败不阻塞全局，标记为"解析失败"并在生成报告中列出

### 挑战 17：增量更新中的间接影响遗漏

**问题**：04 定义的变更映射表是基于文件类型的直接映射（Controller 变更 → 能力目录）。但有些影响是间接的——修改一个 Service 方法的返回类型，不仅影响该 Service 相关的约束知识，还可能影响调用该 Service 的 Controller 的能力目录描述和依赖该返回类型的概念知识。

**应对**：

- **一级传播**：变更映射不仅覆盖直接关联的知识条目，还覆盖一层间接关联。变更文件 → 查找引用该文件的所有文件 → 映射到这些文件关联的知识条目
- **AST 依赖图**：利用 AST 查询工具的"谁引用了这个类/方法"能力，建立文件间的依赖图。变更一个文件时，沿依赖图扩散一层
- **保守策略**：当无法确定间接影响范围时，宁可多重新生成几个条目，也不遗漏。过度生成的成本（几次额外的 LLM 调用）远低于遗漏导致的知识库过时

### 挑战 18：`.meta` 与 Git 的协调

**问题**：`.meta` 文件记录 commit hash 和生成时间戳。如果被 git 跟踪，每次生成都会修改该文件产生额外 commit，多人协作时可能冲突。如果不被 git 跟踪，新 clone 的仓库无法做增量更新。

**应对**：

- **`.meta` 应被 git 跟踪**：commit hash 是知识库与仓库代码的关联锚点，必须持久化。新 clone 的仓库需要 `.meta` 来支持增量更新
- **`.meta` 格式设计**：
  ```json
  {
    "baseCommit": "a1b2c3d4",
    "generatedAt": "2026-06-03T10:30:00Z",
    "version": "1.0.0",
    "schemaVersion": "1.0",
    "generatorVersion": "0.1.0",
    "model": "claude-sonnet-4-20250514",
    "stats": {
      "totalEntries": 42,
      "successEntries": 40,
      "failedEntries": 2
    }
  }
  ```
- **增量更新基线**：读取 `.meta` 中的 `baseCommit`，与当前 HEAD 做 `git diff`，得到变更文件列表
- **`.meta` 不存在时**：视为首次生成，自动升级为全量生成

### 挑战 19：Schema 版本演进与向后兼容

**问题**：随着 ai-wiki 迭代，JSON Schema 可能发生变化（新增字段、修改字段类型、调整嵌套结构）。已生成的知识库用旧 Schema 生成，新版本的程序需要能处理旧格式。

**应对**：

- **Schema 版本标记**：在 `.meta` 中记录 `schemaVersion`（如 `"1.0"`）
- **读取兼容**：程序读取现有知识库时，按 `schemaVersion` 选择对应的解析器
- **升级迁移**：全量重建时自动迁移到最新 Schema。增量更新时，如果 Schema 版本不匹配，自动升级为全量重建
- **字段默认值**：新增字段定义默认值，旧知识库缺少该字段时使用默认值填充
- **废弃字段处理**：字段废弃时保留一个版本周期的兼容读取，下个大版本移除

### 挑战 20：提示词工程的可维护性

**问题**：每种知识类型、每个生成阶段、三层策略的每一层都需要不同的提示词。随着知识类型演进和策略调整，提示词数量和组合复杂度快速增长，管理困难。

**应对**：

- **提示词模板化**：将提示词拆分为可组合的片段：
  - `base_system`：通用的角色定义和输出格式要求
  - `type_specific_instructions`：每种知识类型的提取规则和产物示例
  - `phase_context`：生成阶段 1/2/3 的上下文注入指令
  - `strategy_modifier`：上下文分层、拆分合并、精炼轮的附加指令
- **组合逻辑**：最终提示词 = `base_system` + `type_specific_instructions` + `phase_context` + `strategy_modifier`，各片段独立维护
- **提示词版本管理**：提示词模板作为代码仓库中的文件管理（如 `src/prompts/capability-directory.md`），纳入版本控制和 review
- **提示词测试**：用固定的测试输入验证提示词输出是否符合预期，类似 snapshot testing。提示词变更时必须通过测试

## 设计决策

### 为什么选择管线编排而不是 Agent 自主探索

管线编排的核心优势是**可复现性和成本可控**。ai-wiki 面向的场景是"对任意仓库生成知识库"，需要可预算的 LLM 调用成本和一致性的输出质量。Agent 模式下 LLM 的工具调用路径不可预测，相同仓库两次运行可能产出不同的知识库，这对知识库的可维护性是不可接受的。

LLM 的价值在于对给定上下文的理解和归纳，不在于自主探索代码。把好的上下文喂给 LLM，比让 LLM 自己找上下文，产出质量更高且更稳定。

### 为什么选择 JSON 结构化输出而不是 Markdown 直接输出

核心原因是**可校验性**。04 定义的校验体系（结构完整性、证据有效性、跨类型引用一致性）需要对字段做精确提取和程序化校验。Markdown 格式下的字段提取依赖正则匹配，脆弱且不可靠。JSON 格式使校验变成类型检查，可靠性高得多。

JSON 的"不稳定性"通过扁平化 Schema、宽松解析器、API JSON mode 和重试策略来缓解，是工程上可解决的问题。Markdown 格式下校验的"不可靠性"是结构性问题，无法通过工程手段解决。

### 为什么大上下文用三层递进而不是固定策略

固定策略（如"总是拆分"或"总是压缩"）会导致小分组产生不必要的开销，或大分组仍然溢出。三层递进按成本递增触发，小分组直接调用（零额外开销），中等分组用上下文分层（一轮额外 LLM 调用），大分组才用拆分合并（多轮 LLM 调用 + 合并逻辑）。成本与实际需要成正比。

### 为什么 LLM 不参与上下文组装决策

上下文组装需要的是完整性和准确性——确保不遗漏文件、不遗漏调用关系、分组边界对齐物理组织。这些是规则可覆盖的确定性任务。让 LLM 参与上下文组装会引入不确定性（LLM 可能遗漏文件、做出不一致的分组决策），且增加成本和延迟。LLM 的不可替代性在生成环节——对给定上下文的理解、归纳和知识表达。
