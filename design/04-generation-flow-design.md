# 生成流程设计

本文定义 `ai-wiki` 从读取目标仓库到生成 `ai-knowledge/` 知识库的完整流程，包括流程步骤、分组策略、LLM 调用组织、产物校验和增量更新。

本文是规格层（02）和结构层（03）的延伸，用于约束后续实现方案中生成程序的设计。

## 总体流程

生成流程分为 6 个步骤，依次执行：

```
仓库扫描 → AST 图谱构建 → 候选提取与过滤 → 分组与批处理 → LLM 生成 → 产物校验 → 落盘
```

其中"LLM 生成"按 02 定义的三个生成阶段调度执行：

```
生成阶段 1（基础）：概念知识 → 数据模型 → 能力目录（按序生成，后者可引用前者名称）
生成阶段 2（引用）：边界知识、外部系统交互、约束知识、能力关系、跨域业务流程
生成阶段 3（投影）：术语速查表
```

所有步骤完成后，生成程序将校验通过的产物按 03 定义的目录结构写入 `ai-knowledge/`。

## 步骤 1：仓库扫描

### 目标

识别目标仓库中与知识提取相关的文件，排除无关文件。

### 扫描范围

生成程序应识别以下类型的文件：

- 主要源代码文件（各语言的 `.java`、`.ts`、`.go`、`.py`、`.kt` 等）
- 配置文件（`.yml`、`.yaml`、`.properties`、`.json`、`.toml`、`.env` 等）
- 构建配置（`pom.xml`、`build.gradle`、`package.json`、`go.mod`、`Cargo.toml` 等）
- 测试文件（`*Test.*`、`*Spec.*`、`*_test.*` 等）
- 数据库脚本（`.sql`）
- 已有文档（`.md`、`.txt`、`README*`）

### 排除规则

以下目录和文件应排除：

- 二进制文件、图片、字体
- 依赖目录（`node_modules/`、`.m2/`、`vendor/`）
- 构建产物（`target/`、`build/`、`dist/`、`out/`）
- 版本控制（`.git/`）
- IDE 配置（`.idea/`、`.vscode/`）
- 日志文件、临时文件

### 扫描输出

扫描结果是一份文件清单，包含每个文件的路径、类型（源码/配置/测试/文档）和大小，作为后续步骤的输入。

### 敏感信息过滤

扫描阶段应对配置文件中的敏感信息进行标记，防止敏感内容被注入 LLM 上下文或出现在生成的知识库中：

- **敏感字段识别**：识别配置文件中的密码（password、secret、credential）、密钥（apiKey、accessKey、privateKey）、证书路径、数据库连接字符串（含用户名密码部分）等字段
- **脱敏处理**：在将配置文件内容注入 LLM 上下文时，将敏感值替换为占位符（如 `***` 或 `[REDACTED]`），保留键名不变
- **知识库排除**：生成的知识条目中不引用敏感字段的值。边界知识描述配置项的存在和开关状态，不记录密码等敏感内容

## 步骤 2：AST 图谱构建

### 目标

从扫描识别的源代码文件中提取结构化信息，构建可供查询的 AST 图谱。

### 需要提取的结构化信息

AST 图谱应包含以下信息：

- **类/接口/结构体**：名称、包路径、继承关系、实现的接口、注解
- **方法/函数**：签名（名称、参数、返回类型）、注解、方法体内的方法调用关系
- **字段/属性**：名称、类型、可见性、注解
- **import/require**：导入的包和类
- **包/目录结构**：代码的物理组织方式

### 多模块依赖处理

当项目依赖外部模块（同项目其他子模块、公司内部 JAR/包）时，部分实体类和接口定义不在当前仓库的源码中，AST 图谱无法直接解析这些符号：

- **外部模块识别**：扫描构建配置（pom.xml、build.gradle 等），识别项目依赖的内部模块（如 `music-core`、`common-service`）
- **外部模块源码解析**：如果外部模块的源码在本地可访问（如 Maven 本地仓库中的 sources.jar，或 monorepo 中的兄弟目录），一并解析其源码纳入 AST 图谱
- **外部模块符号标注**：当外部模块源码不可访问时，从 import 语句推断外部类的全限定名，在 AST 图谱中标注为"外部模块符号"（仅有名称和所属模块，无字段和方法详情）
- **影响范围**：外部模块符号主要影响概念知识和数据模型的提取——当实体类定义在外部模块时，证据中标注所属模块，概念知识的"代码体现"字段标注外部来源

### 配置文件解析

配置文件不做 AST 解析，但应解析为键值对或结构化数据，支持后续步骤查询配置项。

### 测试文件解析

测试文件应提取测试方法名称、被测方法和断言内容，支持约束知识的提取。

### 注释代码过滤

AST 解析前应过滤纯注释代码，避免将无活跃代码的元素传入 LLM 上下文：

- **全注释文件/类过滤**：如果一个类的所有方法体都被注释（每行以 `//` 或 `/* */` 包裹），该类在 AST 图谱中标记为"全注释"，后续步骤跳过该类
- **注释方法过滤**：如果单个方法的方法体被完全注释，该方法在 AST 图谱中标记为"已注释"，不参与候选提取
- **保留注释内容**：非注释代码中的行内注释和块注释保留，它们可能包含有价值的业务说明

### 已有文档解析

已有文档（README、API 文档、设计文档、注释文档等）不做 AST 解析，但应提取其文本内容。这些文本内容作为 LLM 生成时的辅助上下文，用于：

- 补充业务术语定义（如 README 中描述的业务概念）
- 提供接口说明和参数解释（如 API 文档）
- 辅助 LLM 理解业务背景（如设计文档中的业务逻辑说明）

已有文档的文本内容按文件组织，在 LLM 调用时根据相关性注入到对应分组的输入上下文中。

### AST 查询能力

生成程序需要通过 AST 图谱执行以下查询：

- 按注解/装饰器查找类和方法（如查找所有 `@RequestMapping` 注解的方法）
- 按类名查找其方法、字段和继承关系
- 追踪方法调用链（谁调用了 A、A 调用了谁）
- 获取方法的源代码片段
- 查找配置项的键值对
- 查找引用某个实体类的所有 Service 方法

AST 图谱的具体构建方式（解析工具、存储格式、索引策略）由实现方案定义。

## 步骤 3：候选提取与过滤

### 目标

从 AST 图谱中按 02 定义的各类型提取规则提取候选信息，过滤掉低价值候选。

### 输入与输出

- 输入：AST 图谱 + 配置文件解析结果
- 输出：按知识类型分组的候选列表

### 提取规则

各知识类型的提取规则已在 02 中定义：

- 能力目录：扫描入口定义 → AST 分组
- 概念知识：提取枚举/实体/常量/状态流转/自定义注解 → 命名和包路径过滤
- 边界知识：扫描配置开关 + 分析能力域范围
- 外部系统交互：扫描外部依赖 + 配置文件 + 交互代码
- 约束知识：提取异常/条件判断/事务/schema/测试断言 → 排除通用校验
- 能力关系：构建调用图 + 识别共享实体 + 扫描事件机制
- 数据模型：提取实体关联 + 识别聚合边界
- 跨域业务流程：基于能力关系构建端到端路径 → 过滤单域流程

### 入口类型扩展

能力目录的入口扫描不仅覆盖 HTTP 端点（Controller 方法），还应覆盖以下入口类型：

- **定时任务**：Quartz Job（实现 `Job` 接口或 `@Scheduled` 注解）、Cron 表达式配置的任务、其他调度框架的 Job 定义
- **消息消费者**：消息队列的消费者方法（`@RabbitListener`、`@KafkaListener`、`@SqsListener` 等）
- **事件监听器**：应用事件监听方法（`@EventListener`、`@Subscribe` 等）

这些入口与 HTTP 端点的区别在于没有 HTTP 方法和 URL 路径，访问方式标注为对应的协议类型（如 `QUARTZ OrderUnpaidJob`、`EVENT ScoreListener.handleScore`）。

### 空入口过滤

扫描到的 Controller 类如果没有定义任何入口方法（只有类注解而无方法），应在候选提取阶段过滤掉，不传入 LLM 上下文。空 Controller 可能出现在以下场景：

- 预留的 Controller 类（仅 `@RestController` 注解，无方法体）
- 重构后遗留的空壳

过滤规则：如果一个类被标注为入口类（有 `@RestController`、`@Controller`、路由注解等），但其中没有任何方法被标注为入口方法，则整个类从能力目录候选中排除。

### 候选信息

每条候选应包含：

- 候选的代码元素（类名、方法签名、字段等）
- 代码位置（文件路径 + 行号或函数名）
- 相关代码片段（方法体、注解声明等）
- 关联上下文（被谁调用、引用了什么类、配置值等）

这些信息将作为 LLM 生成时的输入上下文。

## 步骤 4：分组与批处理

### 目标

将候选信息组织为合理的分组，使每个分组可在一次 LLM 调用中处理。

### 分组原则

- **语义相关性**：同一组内的候选应有足够的上下文关联，使 LLM 能理解它们之间的关系
- **规模可控**：每个分组的代码上下文总量应适配 LLM 的上下文窗口
- **边界清晰**：分组的边界应对齐代码的物理组织（包、类、模块），避免把一个内聚的代码单元拆散

### 各知识类型的分组粒度

| 知识类型 | 分组粒度 | 理由 |
|---------|---------|------|
| 能力目录 | 按 Controller 或路由模块（= 能力域） | 一个域对应一个文件，LLM 需要一次看到域内所有操作以生成一致的命名 |
| 概念知识 | 按包路径聚合相关类 | 同一个包内的枚举和实体往往属于同一业务领域，LLM 可判断合并 |
| 边界知识 | 按能力域聚合配置项和能力信息 | 边界知识与能力域强关联 |
| 外部系统交互 | 按外部系统或 SDK 聚合 | 同一个外部系统的使用代码分散在多处，需要聚合后让 LLM 归纳 |
| 约束知识 | 按业务场景聚合 | 同一业务场景的多个约束应合并为一条知识 |
| 能力关系 | 按能力域聚合调用链和共享实体 | 同一域内的调用关系应合并为一条关系知识 |
| 数据模型 | 按实体关系图聚合 | 通过外键关联的实体应作为一个聚合一起处理 |
| 跨域业务流程 | 按端到端路径聚合 | 一条完整流程的所有步骤应作为一条知识一起处理 |

### 域合并启发式

当多个 Controller 或路由模块的业务关联度很高时，应合并为一个能力域，而非各自独立。合并判断规则：

- **URL 前缀重叠**：多个 Controller 使用相同或高度重叠的 URL 前缀（如 `/order` 和 `/order-goods`），且操作语义连贯，应合并为一个域
- **共享业务实体**：多个 Controller 操作相同的核心业务实体（如 OrderController 和 OrderGoodsController 都操作 OrderDO），且操作在业务流程上有前后关系，应合并
- **操作数量过少**：单个 Controller 只有 1~2 个操作，且这些操作与另一个 Controller 的业务强关联（如 CartController 的 checkout 与 OrderController 的 submit 在同一个购买流程中），应考虑合并
- **不合并的情况**：即使两个 Controller 操作相关实体，如果它们服务不同的用户角色或不同的业务场景（如 TeacherController 和 StudentController），应保持独立

域合并的决策在"步骤 4：分组与批处理"中由程序规则执行，不依赖 LLM 判断。

### 分组规模控制

每个分组的输入（代码片段 + 提示词）应适配 LLM 的上下文窗口。具体限制由实现方案定义，但应遵循以下原则：

- 单个分组的输入不应超过 LLM 可用上下文窗口的 70%，为输出留足空间
- 当一个分组超出限制时，拆分为子组，并在 LLM 生成后进行结果合并
- 拆分优先在代码的物理边界（类、包）上进行，避免把内聚单元拆散

### 大仓库的特殊处理

当仓库代码量较大时，需要额外的处理策略：

- **能力目录**：单个 Controller 方法过多（超过 20 个）时，方法签名列表作为主输入，方法体代码按需加载
- **概念知识**：单个包内类过多时，按子包或类名前缀做二级分组
- **约束知识**：异常抛出语句过多时，按 Service 类或业务模块分组
- **能力关系**：调用图过大时，按入口方法分组追踪，深度限制为 2~3 层

边界知识、外部系统交互和数据模型的条目数量通常较少（边界 5~15 条、外部系统数量有限、数据模型与实体数量正相关），不需要特殊的大仓库处理策略。

## 步骤 5：LLM 生成

### LLM 调用输入

每次 LLM 调用的输入由以下部分组成：

| 输入组成 | 说明 |
|---------|------|
| 知识类型规格 | 02 中该类型的结构定义和产物示例，使 LLM 知道输出的格式 |
| 候选信息 | 该分组内的候选列表，包含代码片段、位置和上下文 |
| 生成指令 | 指导 LLM 如何从候选信息生成知识条目的指令 |
| 已有名称（生成阶段 2+） | 生成阶段 1 已生成的能力域名称和概念名称，用于跨类型引用的一致性 |
| 已有标签池（增量更新时） | 现有 `_index.md` 中的标签列表，用于标签复用 |

### LLM 调用输出

每次 LLM 调用的输出是符合 02 结构定义的知识条目。输出应满足：

- 包含所有必填字段
- 可选字段在有信息时填写，无信息时省略
- 标签数量为 1~3 个
- 引用使用 03 定义的相对路径格式

### 生成约束

- 输出必须是结构化格式，可被程序解析为 Markdown 文件
- LLM 不应编造输入中未提供的代码路径作为证据
- 跨类型引用必须使用输入中提供的已有名称，不自行创造名称
- 受控推断必须遵守 02 中定义的受控推断约束：推断有证据支撑、不基于命名联想或行业常识、证据不足时降级

### 生成调度

按 02 定义的三阶段执行：

**生成阶段 1（基础）**：概念知识、数据模型、能力目录按顺序生成。概念知识先生成（因为能力目录和操作描述中可能需要引用概念名称），数据模型在概念知识之后（实体关系描述可引用概念名称），能力目录最后（域级业务上下文可引用概念名称）。每个知识类型内部，各分组可并行调用 LLM。

**生成阶段 2（引用）**：边界知识、外部系统交互、约束知识、能力关系、跨域业务流程可并行生成。每个知识类型的 LLM 调用输入中应注入生成阶段 1 的产物名称。

**生成阶段 3（投影）**：`_glossary.md` 从已完成的概念知识中投影，不涉及 LLM 调用，由程序直接提取。

### 索引生成

所有知识条目生成完成后，程序从条目中提取概要信息生成索引文件：

- `index.md`：从每个知识条目文件中提取一级标题和一句话描述。能力目录取域级信息（不取操作级信息），其他类型取条目级信息
- `_index.md`：从该类型下所有条目中提取名称、描述、标签和文件路径
- `_glossary.md`：从概念知识中提取术语、定义、别名和文件路径

索引生成不涉及 LLM 调用，由程序直接组装。

## 步骤 6：产物校验

### 校验维度

对生成的知识条目进行四个维度的校验：

**1. 结构完整性**

- 是否包含所有必填字段
- 标签数量是否在 1~3 范围内
- 格式是否符合 03 定义的详情文件头部格式
- 一级标题是否与条目名称一致

**2. 证据有效性**

- 证据引用的文件路径是否存在于仓库中
- 证据引用是否出现在该条目的生成输入中（防止 LLM 编造路径）
- 来源文件列表中的文件是否实际存在

**3. 跨类型引用一致性**

- 引用的能力名称是否存在于 `capabilities/` 目录
- 引用的概念名称是否存在于 `concepts/` 目录
- 引用路径是否可解析为有效文件
- 被引用的条目名称是否与目标文件一级标题一致

**4. 标签一致性**

- 增量更新时，新条目的标签是否优先复用了已有标签池中的标签
- 语义相同的概念是否使用了相同的标签文本

**5. 内容质量**

02 定义了 3 个语义类质量标准（业务化名称、一句话定位、业务语义描述），这些标准涉及内容质量而非格式校验，无法通过简单的规则检查自动验证。

处理方式：

- 生成指令中应明确嵌入这些标准的要求（如"命名使用业务语言而非代码类名"、"描述必须提供代码本身无法直接传达的业务信息"）
- 可选：使用 LLM 二次评估，用另一个 LLM 调用判断生成内容是否满足 02 的"5 分钟规则"（即 Agent 5 分钟内无法通过读代码得出相同结论）
- 二次评估失败时，重新生成一次并在指令中强化质量要求
- 具体是否启用二次评估由实现方案决定

### 校验不合格的处理

| 校验问题 | 处理方式 |
|---------|---------|
| 结构不完整 | 重新生成一次，补充缺失字段提示 |
| 证据路径无效 | 移除无效证据引用，标记为警告 |
| LLM 编造路径 | 丢弃该条目，记录到生成报告 |
| 跨类型引用名称不匹配 | 用实际名称修正引用，重新生成 |
| 标签不一致 | 替换为已有标签池中的匹配标签 |

校验后仍不合格的条目应丢弃，不写入知识库，并记录到生成报告中供人工审查。

## 增量更新

### 变更检测

增量更新通过以下方式检测仓库变化：

- Git diff：比较当前分支与上次生成时的 commit 差异
- 文件变更清单：确定新增、修改、删除的文件

上次生成时的 commit hash 存储在 `ai-knowledge/.meta` 文件中，供下次增量更新时作为基线。`.meta` 文件同时记录上次生成的时间戳和知识库版本号。

### 变更映射

文件变更需要映射到受影响的知识条目：

| 文件变更类型 | 影响的知识条目 |
|------------|-------------|
| Controller / 路由文件变更 | 对应能力域的能力目录文件 |
| 枚举 / 实体类变更 | 对应的概念知识文件 |
| Service 类变更 | 相关的约束知识、能力关系、跨域业务流程文件 |
| 配置文件变更 | 相关的边界知识、外部系统交互文件 |
| 实体类字段变更 | 相关的数据模型文件 |
| 测试文件变更 | 相关的约束知识文件（测试断言是约束知识的提取来源） |
| 已有文档变更 | 可能影响所有引用该文档作为证据的知识条目 |
| 新增文件 | 根据文件类型判断应新增的知识条目 |
| 删除文件 | 标记关联知识条目为待审查 |

### 更新策略

- 只重新生成受影响的知识条目，不全量重建
- 更新受影响的 `_index.md`
- 从最新的概念知识重新生成 `_glossary.md`
- 从所有条目的最新状态重新生成 `index.md`
- 更新标签池：读取现有 `_index.md` 中的标签，增量添加新标签
- 保留未受影响条目的生成时间不变

### 全量重建触发

当变更文件数量超过仓库总文件数的一定比例（如 50%）时，自动升级为全量重建，以保证知识库整体一致性。

## 错误恢复

### LLM 调用失败

- 调用失败（网络错误、超时、速率限制）时重试，采用指数退避策略
- 重试次数由实现方案定义
- 重试仍失败时，该分组标记为生成失败，不阻塞其他分组

### 生成结果不可用

- LLM 返回的内容无法解析为预期格式时，重试一次
- 重试仍失败时，该分组标记为生成失败

### 部分失败处理

- 某个分组生成失败不影响其他分组的生成和校验
- 最终生成报告应列出成功和失败的分组

## 生成报告

每次生成（包括全量生成和增量更新）完成后，生成程序应输出一份生成报告，包含：

- 生成统计：成功条目数、失败条目数、丢弃条目数
- 校验结果汇总：各维度的通过率和典型问题
- 标签池变更：新增的标签、废弃的标签
- 增量更新信息（如适用）：变更文件数、受影响条目数、未受影响条目数
- 失败详情：每个失败分组的分组信息和失败原因

生成报告的格式由实现方案定义。

## 设计决策

### 为什么分组粒度对齐代码的物理组织

LLM 生成知识时需要足够的上下文来理解代码元素之间的关系。如果分组在物理边界（类、包、模块）上拆分，LLM 看到的是一个内聚的代码单元，能生成更准确的命名和描述。如果在物理边界中间拆分（如把一个 Controller 的方法分给两个分组），LLM 缺少完整上下文，可能生成不一致的命名。

### 为什么生成阶段 2 需要注入生成阶段 1 的名称

约束知识、边界知识、能力关系知识和跨域业务流程在生成时需要引用能力目录中的能力域名称和概念知识中的概念名称。如果不注入已有名称，LLM 会自行创造引用名称，导致跨类型引用不一致。注入名称是保证引用一致性的最低成本方式。

### 为什么增量更新不全量重建

全量重建的 LLM 调用成本与仓库规模成正比。对于大型仓库，全量重建的成本高且耗时长。增量更新只重新生成受影响的条目，大幅降低计算成本。代价是需要维护文件变更到知识条目的映射关系，但这是可控的复杂度。

### 为什么 _glossary.md 不涉及 LLM 调用

术语速查表是概念知识的投影，所有信息（术语、定义、别名、文件路径）都已存在于概念知识条目中。程序直接提取即可，不需要 LLM 做额外判断。这保证了术语速查表与概念知识的一致性，也降低了生成成本。
