# 设计目标与原则

本文定义 `ai-wiki` 要解决的问题、最终目标、核心原则与成功标准。

本文只定义需求边界与判断标准，不定义具体实现方案。

## 背景

公司已有一套标准化 Harness，用于指导 AI Agent 完成从需求文档到部署上线的全过程。这个过程包括需求讨论与澄清、spec 生成、plan 生成、代码编写、验证和上线前确认。

在这套 Harness 中：

- Skills 规定 Agent 应该如何工作
- Rules 规定 Agent 必须遵守什么标准
- Wiki 提供 Agent 理解系统所需的领域上下文
- Changes 记录单个需求执行过程中发生了什么（不在 ai-wiki 范围内）

`ai-wiki` 关注的是 Wiki 这一部分。Wiki 包含两个层面：

- 知识层：写入目标仓库 `ai-knowledge/` 的结构化知识文件，由 ai-wiki 读取目标仓库中的可见材料并调用 LLM 生成
- 使用层：一个指导 Agent 在 Harness 各阶段检索和引用知识库的 Skill

`ai-wiki` 负责生成知识层产物。Skill 的具体设计不在本文中定义。

AI Agent 在处理需求时，经常需要先理解大量隐含知识：

- 业务术语是什么意思
- 需求属于哪个业务域或系统边界
- 哪些仓库内可见能力与需求相关
- 当前仓库与哪些外部系统存在可见交互
- 哪些约束能从代码、配置、测试或已有文档中确认
- 仓库内能力之间有什么关系
- 仓库内核心业务实体之间有什么关联关系

这些知识通常分散在代码、注释、配置、文档和测试中。如果没有 Wiki 层的稳定知识，Agent 很容易在需求讨论、方案生成、计划拆解和实现判断阶段出现理解片面、定位错误、边界误判或约束遗漏的问题。

## 最终目标

`ai-wiki` 的最终目标是生成一份知识库，使 Agent 在收到新需求文档时，能够基于该知识库获得确定、可追溯的仓库上下文，减少无证据猜测。

以下能力只基于目标仓库中的可见证据生成，包括代码、配置、注释、测试、脚本和已有文档。无法从仓库中可靠推断的信息，不应作为知识库的稳定结论。

知识库只沉淀有仓库可见证据支撑的确定知识；无法确认的信息不进入知识库。

- 能力目录：仓库内可见业务能力及其入口的结构化清单
- 业务概念理解
- 当前仓库可见能力边界判断
- 外部系统交互识别
- 可见约束识别
- 仓库内能力关系理解
- 数据模型关系理解

这里的"正确"不是指知识库替代 Agent 的需求澄清、方案设计、代码阅读或实现判断，而是指它能为 Agent 提供确定、可追溯的仓库上下文，使 Agent 在后续 Harness 流程中减少无证据猜测。

## 目标读者

`ai-knowledge/` 的目标读者是 AI Agent，不是人。

因此，知识库应优先服务 Agent 的任务执行，而不是服务人工阅读体验：

- 内容结构化、标记规范，支持 Agent 通过 Skill 高效检索和引用
- Agent 有上下文窗口限制，知识库应支持分块加载和分层结构（摘要层与详细层），条目间通过引用关联而非互相复制，使 Agent 能按需加载而不必一次读入全部内容
- 表达要明确，避免文学化、宣传化或过度抽象
- 结论要尽量绑定来源、代码位置或证据
- 信息粒度要能支撑 Agent 做决策，而不是只提供概览
- 应明确区分业务概念、能力边界、外部系统交互和可见约束等知识类型

人工可以阅读这些文档，但人工可读性不是第一优先级。

## 要解决的问题

### 1. 仓库内业务能力缺少目录

Agent 拿到需求后，需要知道仓库中有哪些业务能力可以关联。如果缺少 Wiki，Agent 只能临时搜索代码，容易被相似命名、重复概念或历史遗留代码误导。

知识库应帮助 Agent 回答：

- 仓库中有哪些可见业务能力，各自的入口和所属能力域是什么
- 这些能力在代码、配置、测试或已有文档中有哪些证据
- 哪些能力名称相近但含义不同
- 哪些入口或流程值得优先分析

### 2. 业务概念难以理解

代码里的名称不一定能完整表达业务含义。Agent 需要理解仓库中可见的术语、状态、枚举、字段、权限标识、错误码和数据口径。

知识库应帮助 Agent 回答：

- 某个业务概念在当前仓库中如何被命名和使用
- 关键状态、枚举、字段或错误码分别代表什么
- 哪些概念名称相近但代码语义不同
- 哪些业务概念有明确的代码、配置、测试或文档证据

### 3. 当前仓库可见能力边界不清

Agent 需要判断当前仓库中实际实现了哪些能力、暴露了哪些入口、消费了哪些能力，以及哪些行为在当前仓库中不可见。如果缺少这类知识，Agent 容易把仓库外的能力误当作当前仓库内部能力。

知识库应帮助 Agent 回答：

- 当前仓库可见的核心能力是什么
- 当前仓库暴露了哪些入口或对外行为
- 当前仓库消费了哪些外部能力
- 哪些行为在当前仓库中没有可见实现

### 4. 外部系统交互容易遗漏

当前仓库可能通过接口、SDK、服务名、回调、同步逻辑或数据交换与外部系统交互。如果这些交互没有被沉淀，Agent 容易忽略跨系统边界，或者误判外部系统与当前仓库的关系。

知识库应帮助 Agent 回答：

- 当前仓库与哪些外部系统存在可见交互
- 这些交互通过什么接口、SDK、服务名、回调或数据交换体现
- 当前仓库在交互中是调用方、被调用方、数据生产方还是数据消费方
- 哪些外部系统关系有明确的代码、配置、测试或文档证据

### 5. 可见约束容易遗漏

仓库中有些约束不会以显式文档形式出现，而是体现在类型、schema、枚举、状态流转、配置、测试、错误处理、保护逻辑或已有文档中。如果这些可见约束没有被识别，Agent 在后续 Harness 流程中容易做出违反现有行为的判断。

知识库应帮助 Agent 回答：

- 当前仓库中有哪些由代码、配置、测试、注释或已有文档明确体现的约束
- 这些约束作用于哪些业务概念、能力、入口或外部系统交互
- 哪些状态规则、接口契约、兼容性要求或禁止事项有可见证据
- 哪些约束会影响 Agent 后续的需求澄清、spec、plan 或代码判断

### 6. 仓库内能力关系难以理解

Agent 需要理解仓库内可见业务能力之间的组合、依赖、上下游或共享概念关系。如果缺少这类知识，Agent 容易把相关能力割裂看待，导致 spec 或 plan 漏掉联动影响。

知识库应帮助 Agent 回答：

- 哪些业务能力在代码中存在可见关联
- 这些关联通过入口流程、共享数据结构、状态流转、配置或测试体现
- 哪些能力之间存在上下游、组合或依赖关系
- 这些关系有哪些代码、配置、测试或文档证据

### 7. 数据模型关系难以理解

Agent 需要理解仓库内核心业务实体之间的关联关系——一个实体通过什么字段引用另一个实体、实体之间是一对多还是多对多、哪些实体共同构成一个业务聚合。如果缺少这类知识，Agent 在设计数据变更方案时容易遗漏关联实体的联动影响，或者把字段加错实体。

知识库应帮助 Agent 回答：

- 核心业务实体之间有哪些关联关系
- 这些关联通过什么字段或外键体现
- 哪些实体共同构成一个业务聚合（如"课表"由 Course + Courseware 两级构成）
- 修改一个实体时需要联动考虑哪些关联实体

### 8. 多模块项目的知识组织

多模块项目（Maven 多模块、monorepo、微服务仓库）中，代码按模块组织，但业务知识天然跨模块。Agent 需要知道"这个能力属于哪个模块"、"这个概念定义在哪个模块"、"修改共享模块会影响哪些服务"，但当前的知识组织没有模块维度。

知识库应帮助 Agent 回答：

- 当前项目包含哪些模块，各模块的角色和依赖关系是什么
- 某个业务能力、业务概念或约束属于哪个模块
- 共享模块中的实体被哪些服务使用
- 修改某个模块的代码会影响哪些知识条目

## 不解决的问题

`ai-wiki` 不以以下事项为直接目标：

- 替代 Agent 的实时推理、代码阅读和问题分解
- 替代人工评审、业务确认或上线审批
- 生成面向人类的新手教程、产品说明或完整架构书
- 生成无法从仓库可见证据确认的知识
- 生成待确认项、推断项或假设项作为知识库内容
- 生成某个具体需求的验证计划
- 作为代码索引、调用图或实时依赖分析工具
- 沉淀只服务单个需求执行过程的 Changes 信息
- 保证知识库覆盖仓库中所有细枝末节
- 保证基于知识库的后续实现一定正确
- 为目标仓库自动修改业务代码
- 决定某个具体需求的最终实现方案

知识库的职责是提升 Agent 的初始理解质量、能力判断质量、边界判断质量、外部系统交互识别质量、约束识别质量、能力关系理解质量和数据模型理解质量。

## 知识系统与规则系统的边界

`ai-wiki` 生成的是知识系统，不是规则执行系统。

知识系统解决"系统理解问题"：

- 需求可能关联哪些仓库内可见能力
- 需求中的业务概念在仓库中如何体现
- 当前仓库实现了哪些可见能力，哪些行为在仓库中不可见
- 当前仓库与哪些外部系统存在可见交互
- 仓库中有哪些由代码、配置、测试、注释或已有文档明确体现的约束
- 仓库内可见能力之间有什么关系
- 仓库内核心业务实体之间有什么关联关系

规则系统解决"执行问题"：

- 编码规范
- 类型检查
- 测试命令
- CI 流程
- Review 流程
- 提交流程
- 自动化质量门禁

知识库不替代测试、CI、review 或人工确认。

## 产物范围

`ai-wiki` 的直接产物是写入目标仓库 `ai-knowledge/` 的知识库。对于紧耦合多模块项目，知识库位于仓库根目录并包含 `modules.json`；对于松耦合多模块项目，各可部署服务目录下各自包含一份独立的 `ai-knowledge/`。

指导 Agent 检索和引用知识库的 Skill 属于配套使用层，具体设计由后续文档定义。

知识库应表达以下类型的信息：

- 能力知识：仓库中可见的业务能力、入口和所属能力域
- 概念知识：术语、状态、枚举、字段、权限标识、错误码、数据口径和可见状态规则
- 边界知识：已有能力的局限性和仓库边界的特殊说明
- 外部系统交互知识：当前仓库与外部系统之间的可见交互
- 约束知识：由代码、配置、测试、注释或已有文档明确体现的约束
- 能力关系知识：仓库内可见业务能力之间的组合、依赖、上下游或共享概念关系
- 数据模型知识：仓库内核心业务实体之间的关联关系

具体目录结构、文件格式、生成流程和提示词组织方式不在本文中定义。

## 核心原则

### 1. 只沉淀确定知识和受控推断

知识库沉淀两类内容：

- 确定知识：由仓库可见证据直接支撑的事实（如代码中显式声明的类型、枚举、接口定义）
- 受控推断：由 LLM 基于多处可见证据综合得出的结论，且推断过程可追溯到具体证据（如从多个 Service 的代码模式推断出的业务概念分组）

不受控的推断不进入知识库。所谓"不受控"是指：
- 没有代码证据支撑的猜测
- LLM 基于通用知识而非仓库证据做出的判断
- 多次运行结论不一致且无法验证的推断

知识库不输出待确认项或假设项。

### 2. 以仓库可见证据为来源

知识库中的结论应来自目标仓库中的可见证据。

可见证据包括代码、配置、注释、测试、脚本和已有文档。后续解决方案可以决定如何采集和引用这些证据，但不能把仓库外不可验证的信息当作知识库内容。

### 3. 面向 Agent 的系统理解

知识库内容应服务 Agent 对当前仓库的系统理解，而不是服务人工阅读的完整项目介绍。

优先沉淀能帮助 Agent 理解以下问题的知识：

- 需求可能关联哪些仓库内可见能力
- 需求中的业务概念在仓库中如何体现
- 当前仓库有哪些可见能力边界
- 当前仓库与哪些外部系统存在可见交互
- 当前仓库有哪些可见约束
- 仓库内可见能力之间有什么关系
- 仓库内核心业务实体之间有什么关联关系

### 4. 不替代实时工具

知识库不替代代码搜索、调用关系分析、类型检查、测试、CI、review 或人工确认。

知识库可以帮助 Agent 缩小理解范围，但具体需求的方案设计、代码阅读、实现判断和交付验证仍属于后续 Harness 流程。

### 5. 外部系统只记录可见交互

知识库可以记录当前仓库与外部系统之间的可见交互。

可见交互包括接口调用、SDK 使用、服务名、回调入口、数据交换和状态同步代码。知识库不描述外部系统内部行为，也不推断外部系统的真实业务责任。

外部系统是指当前仓库代码库之外的系统或平台，包括同业务线的其他微服务、第三方业务平台、外部业务数据源和第三方平台服务（如对象存储、短信服务、地图服务等）。不包括当前仓库内部的模块、工具库、消息队列、配置中心等基础设施依赖，除非它们承载了明确的跨仓库业务交互通道。

### 6. 知识粒度服务 Harness 流程

知识库不是静态百科，也不是完整代码索引。

合适的知识粒度应能服务 Agent 在 Harness 流程中的需求澄清、spec 生成、plan 生成和代码理解。知识不应细到复制代码细节，也不应粗到只能提供项目概览。

### 7. 一条稳定知识只有一个权威位置

同一条稳定知识在知识库中应只有一个权威来源。

其他位置可以引用、聚合或解释这条知识，但不应复制出多个互相竞争的事实版本。重复会让 Agent 难以判断哪个结论更新、更准确、更应该相信。

## 成功标准

当 `ai-wiki` 生成的知识库被 Agent 用于后续 Harness 流程时，应满足以下标准：

- 知识库提供仓库内可见业务能力的结构化清单，使 Agent 能据此关联需求与能力
- 知识库包含仓库中可见业务概念的定义与代码映射
- 知识库清晰描述当前仓库的可见能力边界与不可见行为
- 知识库记录当前仓库与外部系统之间的可见交互
- 知识库记录由代码、配置、测试、注释或已有文档明确体现的约束
- 知识库描述仓库内可见能力之间的组合、依赖、上下游或共享概念关系
- 知识库描述核心业务实体之间的关联关系
- 知识库中的关键知识可追溯到仓库证据来源
- 多模块项目中，知识条目标注模块归属，Agent 能区分能力和概念的模块边界

## 质量要求

生成的知识库应具备以下质量：

- 准确：重要结论有来源，避免无证据断言
- 可追溯：能回到代码、配置、测试、脚本或已有文档
- 可检索：标题、术语和结构规范化，支持 Skill 高效检索和引用
- 可组合：单个知识片段可以被取出放入后续上下文
- 可维护：仓库变化后能识别哪些知识可能过期
- 可用于理解：能支撑 Agent 在 Harness 流程中对仓库系统形成准确理解，包括能力判断、概念理解、边界判断、外部系统交互识别、约束识别、能力关系理解和数据模型理解

后续文档可以继续定义：
