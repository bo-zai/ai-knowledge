# 讨论背景与结论

## 初始问题

讨论起点来自一篇关于 `Harness Engineering` 的文章，其中把项目知识分为：

- `.harness/rules`
- `.harness/skills`
- `wiki/`
- `changes/`

用户重点关注的是：`wiki 应该怎么建设`。

## 讨论过程中逐步收敛的问题

最初问题是“wiki 怎么建”，后续收敛成更严格的问题：

- 每份文档内部的知识最小粒度应该是什么
- 哪些知识值得沉淀，不能靠想象
- 外部系统、边界、source of truth 如何表达
- 给 Agent 一份新需求后，它如何依赖 wiki 判断“要做什么”
- 怎么验证每条知识真的有用，而不是伪知识

## 最终目标定义

这轮讨论最终把目标定义为：

> 给 Agent 一份新需求文档，它能够基于沉淀的知识系统，正确完成需求归因、业务语义理解、系统边界判断、外部系统影响识别、代码改动定位、约束识别以及验证计划生成。

这里要特别区分：

- `wiki / 知识系统`
  - 负责让 Agent 知道“应该做什么、不能做什么、改哪里、怎么验证”
- `rules / skills / tests / CI`
  - 负责让 Agent 在实现阶段不跑偏，并机械化收口“正确编码”

也就是说：

- 知识系统主要解决 `理解问题`
- 规则和验证系统主要解决 `执行问题`

## 关键结论

### 1. `wiki` 不能被理解成普通知识库

如果目标是服务 AI Agent，那么 `wiki` 的角色不是“给人阅读的大文档”，而是 `按需检索的业务与系统知识层`。

它必须和以下层分开：

- `常驻入口说明`
  - 例如 `AGENTS.md` / `CLAUDE.md` / Owner Index
- `规则 / SOP`
  - 例如评审标准、提交流程、编码规范
- `当前任务上下文`
  - 例如本次需求分析、当前分支进度、待办
- `变更/记忆`
  - 例如最近做了什么、有哪些临时判断

### 2. 知识最小单位不是“页面”，而是 `claim`

单条知识必须能独立回答：

- 它陈述的是什么事实 / 规则 / 决策 / 未知
- 它作用于什么范围
- 它会影响 Agent 哪个判断
- 没有它，Agent 更可能犯什么错
- 它的证据是什么

### 3. 设计起点不是目录，而是 Agent 的决策链

Agent 接到新需求后，会经历至少以下决策链：

1. 需求在说什么
2. 这是谁的责任
3. 系统现在怎么工作
4. 哪些约束不能破坏
5. 代码应该改哪里
6. 改完怎么验证
7. 哪些地方不能猜

知识系统必须精确支持这条链路。

### 4. 外部系统必须是一级知识对象

如果外部系统只作为“背景介绍”，则 Agent 会频繁出现：

- 把外部系统当作本系统改动责任
- 错认 source of truth
- 忽略异步回调、重试、补偿
- 错误理解第三方错误语义

因此：

- 外部系统
- 所有权边界
- 契约
- 失败语义

都必须被建模成明确对象。

### 5. 真正的质量标准是“新需求可读性与可规划性”

不是问：

- 文档是不是写得完整
- 页面看起来是否专业

而是问：

- 给定一个新需求，Agent 的 change plan 是否更准确
- 是否更少错认术语、边界、source of truth
- 是否更少漏掉外部系统、契约、不变量和验证项

## 重要非目标

这轮讨论没有把下面这些作为直接目标：

- 让 wiki 独立保证代码正确
- 让 wiki 成为唯一知识来源
- 自动生成一整套完整文档后即视为完成
- 仅凭“看起来合理”决定知识是否沉淀

## 设计约束

1. 一条稳定知识必须有证据。
2. 没证据但又真实需要的问题，必须进入 `OPEN`，不能伪装成事实。
3. 同一条稳定事实只能有一个权威位置。
4. 组合页只能编排、链接和聚合，不应发明新事实。
5. 文档必须可被评测，而不是只供人工阅读。

## 本轮讨论沉淀的几个核心口号

- `页面不是最小单位，claim 才是`
- `先证据，后定义`
- `先评测，后保留`
- `外部系统不是附录，是一级对象`
- `知识系统解决理解，规则系统解决执行`
