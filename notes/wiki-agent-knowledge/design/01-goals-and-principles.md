# 设计目标与原则

## 最终目标

给 Agent 一份新需求文档，它能够基于沉淀的知识系统，正确完成：

- 需求归因
- 业务语义理解
- 系统边界判断
- 外部系统影响识别
- 代码改动定位
- 约束识别
- 验证计划生成
- 未知升级

## 成功标准

不是"文档看起来完整"，而是：

- Agent 能知道目标仓库有哪些业务能力、外部系统、边界、契约和验证方式
- Agent 接到新需求后，能先做业务理解、边界判断和未知升级，再输出改动计划
- Agent 的关键判断都能引用知识 ID
- 没有知识支撑的判断被显式标记为推测
- 过期或缺失的知识不会被当作稳定事实使用

## 知识系统与规则系统的边界

- **知识系统**解决"理解问题"——Agent 应该做什么、不能做什么、改哪里、怎么验证
- **规则/验证系统**解决"执行问题"——编码规范、测试执行、CI、review、提交流程

知识包不试图独立保证代码正确。

## 核心原则

### 1. 页面不是最小单位，知识段才是

一个知识对象必须能独立回答：

- 它陈述了什么事实或决策
- 它作用于什么范围
- 它影响 Agent 哪个判断
- 没有它，Agent 更可能犯什么错
- 它的证据是什么

但知识段不必每个都独立成文件。只有跨域共享且自身复杂的对象才值得独立存在。

### 2. 设计起点是 Agent 的决策链，不是目录

Agent 接到新需求后的决策链：

1. 需求在说什么
2. 这是谁的责任
3. 系统现在怎么工作
4. 哪些约束不能破坏
5. 代码应该改哪里
6. 改完怎么验证
7. 哪些地方不能猜

知识系统必须精确支持这条链路。

### 3. 外部系统是一级对象

外部系统不能只作为"背景介绍"。如果外部系统没有被显式建模，Agent 会频繁出现：

- 把外部系统当作本系统改动责任
- 错认 source of truth
- 忽略异步回调、重试、补偿
- 错误理解第三方错误语义

外部系统、所有权边界、契约、失败语义都必须被建模成明确对象。

### 4. 先证据，后定义

每条稳定知识必须有证据。没证据但又真实需要的问题必须进入"已知未知"，不能伪装成事实。

### 5. 一条事实只有一个权威位置

同一条知识在整个知识库中只能有一个权威来源。重复意味着失控。

### 6. 能力文档聚合知识，不发明事实

能力文档可以引用、聚合和编排共享对象，但不能发明新的权威事实。

### 7. 先评测，后保留

判断一条知识是否值得沉淀，不靠"看起来有用"，必须回答：

- 没有它时，Agent 是否更容易犯错
- 只有它变化时，结果是否显著变化
- 它是否真的改变了 Agent 的决策

## 非目标

以下不是本设计的目标：

- 让知识包独立保证代码正确
- 让知识包成为唯一知识来源
- 自动生成完整文档后即视为完成
- 凭"看起来合理"决定知识是否沉淀
- 替代代码工具能提供的实时代码结构信息（如调用关系、文件位置）
