# 首轮落地 Playbook

## 目标

在一个真实项目中，以最小成本验证这套知识系统是否真的提升 Agent 的需求理解与 change plan 质量。

## 选域原则

第一批不要选最复杂的全域，而应选一个满足以下条件的能力域：

1. 最近 `90` 天内真实需求较多
2. 至少涉及 `1` 个外部系统或跨模块边界
3. 历史上出现过返工、误判边界或漏验证
4. 能拿到代码、测试、契约、需求和评审证据
5. 修改风险中高，但不是全公司级关键路径

典型候选：

- 支付/退款
- 订单取消/售后
- 用户身份与权限
- 供应链对接
- 消息投递与回调消费

## 第 0 步：建立 working agreement

在真正落盘前，先明确这些约束：

- 稳定知识对象必须绑定证据
- 组合页不能发明新事实
- 没有 `VER` 的能力对象不算 ready
- 没有 `OPEN` 的体系默认不成熟
- 删除知识对象是正常操作，不是失败

## 第 1 步：建立 Need Ledger

从真实摩擦里抽样，不要从脑海里想象。

优先来源：

- 近 `20` 个需求
- 近 `20` 个返工 PR
- 近 `10` 个 incident / bugfix
- 高频 onboarding 问题
- AI 或人工评审中重复出现的问题

目标：

- 标出高频误解点
- 标出高频边界错误
- 标出高频验证缺失

产出：

- 一份 `Need Ledger`

## 第 2 步：建立 Evidence Ledger

对每个高频问题，去找一手证据。

优先顺序：

1. 代码
2. 测试
3. schema / 契约 / 配置
4. ADR / PR / incident

目标：

- 明确哪些知识是真有证据
- 明确哪些地方其实还未知

产出：

- 一份 `Evidence Ledger`

## 第 3 步：抽出 Claim Candidates

不是把证据直接写成文档，而是先提炼 `claim`。

要求每条 claim 必须回答：

- 它是什么
- 它影响 Agent 哪个判断
- 缺了它会怎么错
- 过期后会怎么错

产出：

- `10` 到 `20` 条候选 claims

## 第 4 步：选 3 个 gold cases

建议三个 case 分别代表：

1. 术语理解复杂
2. 边界/外部系统复杂
3. 验证/补偿复杂

要求：

- 都必须来自真实历史需求
- 都必须能标注出正确答案
- 至少 `1` 个 case 应该是高风险 case

## 第 5 步：创建首批对象

第一批对象只做：

- `TERM`
- `SYS`
- `OWN`
- `CON`
- `MOD`
- `VER`
- 必要时加少量 `OPEN`

不建议第一轮就全量做 `FLOW / STATE / INV / DEC`，除非 case 已明确依赖它们。

## 第 6 步：创建 capability 组合页

规则：

- 只聚合对象
- 不新增事实
- 用于指导 Agent 读取顺序

## 第 7 步：建立 catalog.yaml

首版只需满足：

- 能按 capability 找到 seed objects
- 能按关键词触发对象
- 能按对象路由到文件
- 能识别升级提问条件

## 第 8 步：跑 requirement -> plan 评测

每个 case 至少跑三组：

- `with_full_knowledge`
- `without_key_object`
- `with_stale_object`

记录：

- 术语映射是否更准
- source of truth 是否更准
- 改动定位是否更准
- 验证计划是否更完整
- unsupported assumptions 是否下降

## 第 9 步：清理对象

以下对象优先删除或降级：

- 检索到了但不改变决策
- 没有一手证据
- 只是显性代码事实
- 和别的对象重复
- 明显 stale

## 第 10 步：扩展第二批对象

只有首轮评测确认有效后，再补：

- `FLOW`
- `STATE`
- `INV`
- `DEC`
- `ACTOR`

## 最小成功标准

首轮成功，不要求一切完整，只要求：

1. 至少 `1` 个能力域完成对象化
2. 至少 `3` 个真实 case 有 `gold`
3. 至少 `1` 个核心指标有可观测提升
4. 至少删掉 `1` 条“看起来有用但实际上无效”的伪知识
