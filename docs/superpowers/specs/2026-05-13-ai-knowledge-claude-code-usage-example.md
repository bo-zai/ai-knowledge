# Claude Code 生成 AI Knowledge 的实际运行示例

日期：2026-05-13

## 1. 说明

本文档提供一套可直接复制到 Claude Code 的实际运行示例。

假设前提是：

1. 你已经在目标代码仓库根目录启动了 Claude Code。
2. 你希望在该仓库内直接生成一套 `ai-knowledge/wiki/` 文档。
3. 你优先让 Claude Code 自己扫描仓库内材料，再由你补充仓库外材料。

使用前，只需要替换下面这些占位符：

1. `<外部系统A>`、`<外部系统B>`
2. `<本地系统或服务A>`
3. `<核心业务对象A>`、`<核心字段或状态A>`
4. `<核心能力A>`、`<核心能力B>`
5. `<仓库外材料>`

如果没有仓库外材料，可以直接写“无”，并要求 AI 在相关结论处输出“待人工确认”。

## 2. 第一次运行：生成第一批原子事实卡

```text
你现在在一个真实代码仓库中工作。你的任务是：先从当前仓库自行收集可用材料，再批量起草一组面向 AI 检索和理解的业务知识文档，输出为多个 Markdown 文件。

严格遵守下面规则：

1. 先自行扫描当前仓库中的本地材料，包括但不限于：README、docs、架构文档、接口定义、配置文件、测试代码、关键模块代码、脚本、SQL、迁移文件。
2. 对于能从当前仓库直接确认的技术事实，可以直接写入文档。
3. 对于不能从当前仓库可靠确认的业务边界、责任归属、事实来源、前置依赖、验收口径，不允许凭常识补全，必须标记“待人工确认”。
4. 文档是给 AI 检索和理解用的，不是给人培训用的。不要写解释性话术。
5. 每篇文档必须原子化，只围绕单一对象展开。
6. 默认优先使用正文和表格承载关键信息。除非我明确要求，否则不要生成图片型图表。
7. 如果生成 Mermaid 图，它只能作为辅助总览，不能替代表格或正文中的正式结论。
8. 输出多个文件时，严格使用下面格式：

=== FILE: <相对路径> ===
<Markdown 内容>

9. 如果你在仓库中找不到某类材料，不要假设它存在；应在对应文档中标记材料缺失和待人工确认项。
10. 不要输出你的搜索过程，不要输出任务说明，只输出文件内容。

【知识库根目录】
ai-knowledge/wiki/

【本批次目标文档】
1. 业务全景/系统地图.md
2. 外部系统/<外部系统A>.md
3. 外部系统/<外部系统B>.md
4. 业务对象与口径/<核心业务对象A>.md
5. 业务对象与口径/<核心字段或状态A>.md
6. 业务能力/<核心能力A>.md
7. 业务能力/<核心能力B>.md

【可额外补充的仓库外材料】
<仓库外材料；如果没有就写“无”>

【输出要求】
1. 先用仓库内材料起草
2. 仓库外材料没有提供时，涉及边界结论的地方标记“待人工确认”
3. 每个文件使用 === FILE: ... === 包裹
```

## 3. 第二次运行：生成流程、触点、API、本地代码落点

建议在你快速看过第一批文档、修正明显边界问题后，再执行第二次运行。

```text
继续基于当前仓库和已生成的 ai-knowledge 文档，生成第二批流程与技术映射文档。

仍然遵守之前的所有规则，特别是：
1. 不能凭常识补全边界。
2. 默认优先正文和表格，不要生成图片型图表。
3. Mermaid 只能辅助，不能替代表格和正文中的正式结论。
4. 不能确认的地方写“待人工确认”。

【知识库根目录】
ai-knowledge/wiki/

【本批次目标文档】
1. 流程与交接/<核心流程A>.md
2. 流程与交接/<核心流程B>.md
3. 集成触点/<入站事件或接口A>.md
4. 集成触点/<出站接口或查询A>.md
5. api/<本地业务接口A>.md
6. 本地代码落点/<本地系统或服务A>.md
7. 本地代码落点/<关键模块A>.md
8. 本地代码落点/<关键模块B>.md
9. 本地代码落点/实现层次规则.md

【生成要求】
1. 流程卡必须包含：起点、关键步骤、责任归属、异常处理。

3. API 卡必须包含：接口职责、关键返回字段、高频变更、不应承担的职责。
4. 本地服务或模块卡必须包含：职责、上下游依赖、高频改动点、禁改或慎改区域。
5. 实现层次规则必须明确每一层负责什么、不负责什么，并给出常见错误。

【可额外补充的仓库外材料】
<仓库外材料；如果没有就写“无”>

【输出格式】
=== FILE: <相对路径> ===
<Markdown 内容>
```

## 4. 第三次运行：生成需求决策卡

```text
继续基于当前仓库和已生成的 ai-knowledge 文档，生成第三批需求决策文档。

仍然遵守之前的所有规则，特别是：
1. 对外部系统边界、事实来源、主责归属、前置依赖、验收标准，材料不足时必须写“待人工确认”。
2. 不要把需求路由、实现方式判断、前置依赖、验收口径混成一篇综述。
3. 默认优先正文和表格，不要生成图片型图表。

【知识库根目录】
ai-knowledge/wiki/

【本批次目标文档】
1. 需求路由/<高频需求类型A>.md
2. 需求路由/<高频需求类型B>.md
3. 需求路由/<高频需求类型C>.md
4. 实现方式判断/<高频需求类型A>.md
5. 实现方式判断/<高频需求类型B>.md
6. 前置依赖与协作/<前置依赖主题A>.md
7. 前置依赖与协作/<前置依赖主题B>.md
8. 规则与反例/<核心规则A>.md
9. 规则与反例/<常见误判案例集>.md
10. 验证与验收/<核心场景A>.md
11. 验证与验收/<核心场景B>.md

【生成要求】
1. 需求路由卡必须包含：适用范围、标准判断顺序、标准处理路径、不应走的路径。
2. 实现方式判断卡必须包含：默认落地方式、何时需要改代码、何时不需要改代码、何时还需要协作。

4. 规则卡必须是可执行规则。
5. 误判案例必须包含：原始需求、错误判断、正确判断、错误原因、正确阅读路径。
6. 验收卡必须写成可执行验收口径。

【可额外补充的仓库外材料】
```

## 5. 第四次运行：生成导航文档

```text
基于当前 ai-knowledge/wiki/ 下已经生成的文档，生成导航类文档。

仍然遵守之前的所有规则，特别是：
1. 导航文档只能总结和引导，不要引入新业务事实。
2. 如果已有文档中某些边界结论仍是“待人工确认”，导航文档里不要把它写成确定结论。
3. 默认优先正文和表格，不要生成图片型图表。

【知识库根目录】
ai-knowledge/wiki/

【本批次目标文档】
1. index.md
2. doc-map.md
3. getting-started.md
4. 业务全景/_index.md
5. 外部系统/_index.md
6. 业务能力/_index.md
7. 业务对象与口径/_index.md
8. 流程与交接/_index.md
9. 集成触点/_index.md
10. 需求路由/_index.md
11. 实现方式判断/_index.md
12. 本地代码落点/_index.md
13. 前置依赖与协作/_index.md
14. 规则与反例/_index.md
15. 验证与验收/_index.md
16. api/_index.md

【生成要求】
1. index.md 包含：业务范围、核心边界结论、文档分区、高频需求清单。
2. doc-map.md 按“问题 -> 先读文档 -> 结论类型”的方式组织。
3. getting-started.md 写收到新需求后的最短阅读路径。
4. 各 _index.md 只做目录摘要和阅读指引。

【输出格式】
=== FILE: <相对路径> ===
<Markdown 内容>
```

## 6. 第五次运行：做一轮自检

```text
你现在不是继续生成文档，而是审查当前 ai-knowledge/wiki/ 下已生成的知识文档。

任务：
1. 找出哪些结论是有明确材料支持的。
2. 找出哪些结论只是推测，应该改成“待人工确认”。
3. 找出哪些文档之间存在冲突。
4. 找出哪些关键知识缺失，导致 AI 后续无法稳定生成准确 Plan。

输出格式：
1. 确定性结论
2. 待人工确认项
3. 冲突项
4. 缺失项
5. 建议补充的文档

审查重点：
- 系统边界
- 事实来源
- 能力归属
- 是否需要改本地代码
- 本地改动范围
- 前置依赖
- 验收标准

要求：
1. 直接基于当前 ai-knowledge/wiki/ 文档做审查。
2. 不要重写文档正文。
3. 不要输出空泛总结。
```

## 7. 你真正需要做的人工动作

每一批生成后，优先人工修正下面这些内容，而不是先修文风：

1. 外部系统边界
2. 事实来源
3. 主责归属
4. 前置依赖
5. 验收口径

## 8. 最小建议

第一次运行时，不要生成太多文档。

建议先选：

1. 2 个外部系统
2. 1 个本地系统
3. 2 个核心业务对象
4. 2 个核心能力
5. 2 个高频需求类型

这样最容易形成第一版可用知识树，也最方便你快速人工纠偏。
