# `ai-knowledge` 目录级建设策略

日期：2026-05-13

## 1. 文档目的

上一份文档已经回答了“哪些知识适合自动化沉淀、哪些只能人工填写”。

本文档进一步回答一个更落地的问题：

**在当前 `ai-knowledge/` 目录结构下，每个分区应该如何建设，采用哪种生成方式，AI 和人工分别承担什么责任。**

本文档的目标不是再抽象讨论“知识类型”，而是直接把建设策略映射到现有目录：

1. 哪些目录适合自动生成
2. 哪些目录适合 AI 起草
3. 哪些目录必须人工主写
4. 各目录的默认数据来源是什么
5. 各目录进入知识库前需要什么级别的人工确认

## 2. 建设策略总览

建议把 `ai-knowledge` 的内容建设分成三层：

### 2.1 技术事实层

特点：

1. 主要来自代码、接口、Schema、消息定义、调用链
2. 结构性强
3. 可自动刷新
4. 错误通常容易通过技术手段校验

典型目录：

1. `api`
2. `集成触点`
3. `本地代码落点`
4. 部分 `术语与别名`

推荐建设方式：

`自动生成 + 人工抽查`

### 2.2 业务判断候选层

特点：

1. 来自代码、需求、PR、工单、设计文档的综合分析
2. 可以由 AI 总结，但不宜直接当成权威答案
3. 需要领域人员做边界修正

典型目录：

1. `业务全景`
2. `业务能力`
3. `业务对象与口径`
4. `流程与交接`
5. `需求路由`
6. `验证与验收`

推荐建设方式：

`AI 起草 + 人工确认`

### 2.3 权威口径层

特点：

1. 强依赖组织边界、业务归属、协作约束
2. 不在代码里，或者不能仅凭代码得出结论
3. 一旦写错，会直接误导 AI 的边界判断

典型目录：

1. `外部系统`
2. `实现方式判断`
3. `前置依赖与协作`
4. `规则与反例`
5. `本地代码落点` 中的禁改区说明

推荐建设方式：

`人工主写 + AI 辅助补充`

## 3. 顶层文档建设策略

### 3.1 `index.md`

### 推荐建设方式

`AI 起草 + 人工确认`

### AI 可自动完成的部分

1. 汇总已有系统清单
2. 汇总核心分区和入口
3. 汇总高频需求类型

### 必须人工确认的部分

1. 知识树覆盖范围
2. 核心边界结论
3. 哪些内容属于当前业务域，哪些不属于

### 原因

首页是全局口径入口，虽然可以由 AI 汇总事实，但边界范围必须人工拍板。

---

### 3.2 `architecture.md`

### 推荐建设方式

`AI 起草 + 人工确认`

### AI 可自动完成的部分

1. 发现系统之间的调用或交互关系
2. 发现本地服务和模块关系
3. 生成候选结构图

### 必须人工确认的部分

1. 关系图是否反映真实业务层次，而不只是技术调用关系
2. 哪些关系是正式链路，哪些只是临时或历史兼容链路

### 原因

架构图如果只是代码调用图，会误导 AI 以为“有调用就有主责”。

---

### 3.3 `getting-started.md`

### 推荐建设方式

`人工主写 + AI 辅助整理`

### AI 可自动完成的部分

1. 汇总高频入口文档
2. 生成候选阅读路径

### 必须人工确认的部分

1. 读取顺序
2. 进入编码前必须确认的事项

### 原因

这是知识树使用协议，属于规则类内容，不适合完全自动生成。

---

### 3.4 `doc-map.md`

### 推荐建设方式

`AI 起草 + 人工确认`

### AI 可自动完成的部分

1. 建立问题到目录的初步映射
2. 扫描文档之间的交叉引用关系

### 必须人工确认的部分

1. 哪类问题的优先阅读路径是什么
2. 冲突时应该信哪个目录

## 4. 各分区建设策略

### 4.1 `业务全景`

### 推荐建设方式

`AI 起草 + 人工裁边界`

### 默认数据来源

1. 架构文档
2. 系统 README
3. 需求背景说明
4. 仓库依赖关系

### AI 可自动生成的内容

1. 系统候选清单
2. 本地系统间关系
3. 候选业务域描述

### 人工必须补充的内容

1. 哪些系统属于当前知识树范围
2. 哪些系统只是背景系统
3. 业务域边界定义

### 建议节奏

1. AI 先生成候选系统地图
2. 人工删除不相关系统
3. 人工补充边界结论

---

### 4.2 `术语与别名`

### 推荐建设方式

`AI 发现 + 人工定标准叫法`

### 默认数据来源

1. 需求文档
2. 接口文档
3. 历史工单
4. 代码命名
5. 设计文档

### AI 可自动生成的内容

1. 同义词、简称、旧名
2. 高概率术语映射
3. 同名字段和对象候选

### 人工必须补充的内容

1. 标准名称
2. 是否完全同义
3. 哪些词是误用或历史脏口径

### 原因

AI 很适合发现别名，但不适合直接决定“以后团队应该用哪个词作为标准口径”。

---

### 4.3 `外部系统`

### 推荐建设方式

`人工主写 + AI 辅助补证据`

### 默认数据来源

1. 组织边界信息
2. 接口依赖
3. 系统清单
4. 需求协作记录

### AI 可自动生成的内容

1. 候选外部系统列表
2. 与外部系统有关的接口、事件、SDK、域名
3. 与本地系统的交互证据

### 人工必须补充的内容

1. 它是不是外部系统
2. 是否允许直接修改
3. 它负责什么，不负责什么
4. 它与本地系统的正式责任边界

### 原因

外部系统不是技术概念，而是组织边界概念。AI 可以发现“有交互”，不能决定“它是不是外部系统”。

---

### 4.4 `业务能力`

### 推荐建设方式

`AI 起草 + 人工定主责`

### 默认数据来源

1. 需求文档
2. 代码模块名
3. 服务说明
4. PR 和工单历史

### AI 可自动生成的内容

1. 候选能力清单
2. 参与该能力的系统列表
3. 该能力在本地系统中的实现痕迹

### 人工必须补充的内容

1. 正式主责系统
2. 协作方与消费方
3. 历史下沉逻辑是否仍然代表正式归属

### 原因

能力是最容易被代码“假象”误导的一层，因为代码里可能存在本地实现，但责任并不一定在本地。

---

### 4.5 `业务对象与口径`

### 推荐建设方式

`AI 抽取对象清单 + 人工定事实来源`

### 默认数据来源

1. Schema
2. DTO
3. 数据库表
4. API 返回字段
5. 需求文档

### AI 可自动生成的内容

1. 对象和字段清单
2. 字段传递路径
3. 同名对象和字段候选

### 人工必须补充的内容

1. 事实来源系统
2. 本地是否拥有定义权
3. 本地存储身份是主数据、副本还是衍生视图

### 原因

对象和字段很适合自动发现，但“语义归属”必须人工定口径。

---

### 4.6 `流程与交接`

### 推荐建设方式

`AI 起草流程 + 人工定责任`

### 默认数据来源

1. 调用链
2. 任务编排
3. 事件流
4. 设计文档
5. 需求说明

### AI 可自动生成的内容

1. 候选流程步骤
2. 本地链路起止点
3. 系统间交互顺序

### 人工必须补充的内容

1. 每一步的责任归属
2. 异常和补偿规则
3. 流程中的人工协作步骤

---

### 4.7 `集成触点`

### 推荐建设方式

`自动生成 + 人工抽查`

### 默认数据来源

1. OpenAPI
2. HTTP 客户端代码
3. 消息消费者和生产者
4. Schema 文件
5. 批处理任务

### AI 可自动生成的内容

1. API、事件、Topic、文件交互点
2. 调用方向
3. 关键字段
4. 本地入口位置

### 人工必须补充的内容

1. 哪些触点已废弃或仅用于兼容
2. 哪些触点属于正式长期契约

### 原因

集成触点是最稳定、最结构化的一类技术事实，优先适合自动化建设。

---

### 4.8 `需求路由`

### 推荐建设方式

`AI 归纳候选 + 人工确认`

### 默认数据来源

1. 历史需求
2. PR
3. 代码改动位置
4. 复盘材料

### AI 可自动生成的内容

1. 候选需求类型
2. 某类需求经常改哪些服务和模块
3. 候选标准处理路径

### 人工必须补充的内容

1. 当前仍然推荐的处理路径
2. 哪些历史改法其实不应复用
3. 哪些路径应明确排除

### 原因

需求路由非常有价值，但如果直接从历史代码反推，很容易把历史错误路径升格为标准路径。

---

### 4.9 `实现方式判断`

### 推荐建设方式

`人工主写 + AI 给候选`

### 默认数据来源

1. 历史需求处理方式
2. 运维手册
3. 配置中心说明
4. 规则表和脚本
5. 协作记录

### AI 可自动生成的内容

1. 某类需求曾经走过代码、配置或数据处理
2. 系统内是否存在配置扩展点或规则表
3. 某类需求可能的候选处理方式

### 人工必须补充的内容

1. 这类需求当前默认应走什么方式
2. 在什么条件下不应该写代码
3. 在什么条件下必须等待上游或联调

### 原因

这是决定 Plan 会不会“把非代码问题写成代码方案”的关键目录，因此必须人工拍板。

---

### 4.10 `本地代码落点`

### 推荐建设方式

`自动生成主体 + 人工补禁区和推荐改法`

### 默认数据来源

1. 代码目录
2. 调用链
3. 入口点
4. 集成适配代码
5. 测试目录

### AI 可自动生成的内容

1. 本地服务和模块清单
2. 关键入口位置
3. 上游字段涉及的本地模块
4. 调用链上的关键路径

### 人工必须补充的内容

1. 慎改区、禁改区
2. 推荐改动方式
3. 哪些模块虽然相关但不应改

### 原因

代码落点本身很适合自动化，但“推荐改法”和“禁区”不在代码里。

---

### 4.11 `前置依赖与协作`

### 推荐建设方式

`人工主写 + AI 补候选阻塞项`

### 默认数据来源

1. 联调记录
2. 发布流程
3. 运维文档
4. 白名单和权限说明
5. 历史阻塞项

### AI 可自动生成的内容

1. 候选依赖清单
2. 上游接口、权限、事件、环境等可能前置项
3. 历史相似需求中的常见阻塞

### 人工必须补充的内容

1. 当前真实阻塞项
2. 哪些事项由谁负责推动
3. 哪些依赖满足前不能交付

### 原因

前置依赖本质上是协作和流程信息，不在代码里。

---

### 4.12 `规则与反例`

### 推荐建设方式

`人工主写 + AI 整理材料`

### 默认数据来源

1. 事故复盘
2. PR 评论
3. Bug 单
4. 历史错误需求分析

### AI 可自动生成的内容

1. 候选误判案例
2. 高重复错误模式
3. 反例摘要草稿

### 人工必须补充的内容

1. 哪些案例真正值得沉淀为规则
2. 哪条规则是正式口径
3. 哪些“错误”只是历史合理方案

### 原因

反例和规则是高价值纠偏知识，但最容易因为误读历史而写偏。

---

### 4.13 `验证与验收`

### 推荐建设方式

`AI 起草检查清单 + 人工定验收标准`

### 默认数据来源

1. 测试代码
2. 联调脚本
3. 发布 checklist
4. 历史回归项

### AI 可自动生成的内容

1. 最小验证步骤候选
2. 相关联调点候选
3. 常见漏测点候选

### 人工必须补充的内容

1. 当前版本的正式验收项
2. 哪些测试必须执行
3. 哪些联调必须完成

### 原因

AI 可以生成很好的验证草稿，但不能代替业务和交付标准。

---

### 4.14 `api`

### 推荐建设方式

`自动生成 + 人工补语义说明`

### 默认数据来源

1. OpenAPI
2. Controller / Handler
3. DTO 和 Schema
4. 接口测试

### AI 可自动生成的内容

1. 接口路径
2. 参数
3. 返回字段
4. 本地处理链

### 人工必须补充的内容

1. 字段的业务含义
2. 哪些字段属于正式长期承诺
3. 哪些字段只是兼容输出

## 5. 顶层优先建设顺序

如果从零开始建设，建议顺序如下：

### 第一批：优先自动生成

1. `集成触点`
2. `本地代码落点`
3. `api`
4. `术语与别名` 的候选清单

目的：

先快速建立技术事实层，让 AI 至少知道本地系统是怎么连起来的。

### 第二批：AI 起草后人工确认

1. `业务对象与口径`
2. `业务能力`
3. `流程与交接`
4. `需求路由`
5. `验证与验收`

目的：

在技术事实层基础上，形成可供 Plan 使用的业务判断层。

### 第三批：人工主写

1. `外部系统`
2. `实现方式判断`
3. `前置依赖与协作`
4. `规则与反例`
5. `业务全景` 的边界口径

目的：

给 AI 最后补上真正决定边界和责任的知识。

## 6. 每个目录的进入知识库门槛

为了避免 AI 直接使用未经确认的候选知识，建议不同目录采用不同门槛：

| 目录 | 可否自动入库 | 推荐门槛 |
|---|---|---|
| `集成触点` | 可以 | 自动生成后人工抽查 |
| `本地代码落点` | 可以 | 自动生成后人工补禁区 |
| `api` | 可以 | 自动生成后人工补语义 |
| `术语与别名` | 谨慎 | 至少人工确认标准术语 |
| `业务能力` | 不建议直接入库 | 必须人工确认主责 |
| `业务对象与口径` | 不建议直接入库 | 必须人工确认事实来源 |
| `流程与交接` | 不建议直接入库 | 必须人工确认责任交接 |
| `需求路由` | 不建议直接入库 | 必须人工确认标准路径 |
| `实现方式判断` | 不可自动入库 | 必须人工主写 |
| `外部系统` | 不可自动入库 | 必须人工主写 |
| `前置依赖与协作` | 不可自动入库 | 必须人工主写 |
| `规则与反例` | 不可自动入库 | 必须人工主写 |
| `验证与验收` | 不建议直接入库 | 必须人工确认验收项 |

## 7. 最终建议

在 `ai-knowledge` 目录下建设知识时，不要追求“所有目录统一采用一种生成方式”。

更合理的策略是：

1. 让 `集成触点`、`本地代码落点`、`api` 成为自动化主战场。
2. 让 `业务能力`、`业务对象与口径`、`流程与交接`、`需求路由` 成为 AI 起草主战场。
3. 让 `外部系统`、`实现方式判断`、`前置依赖与协作`、`规则与反例` 成为人工口径主战场。

这样建设的好处是：

1. 自动化效率高
2. 人工工作量集中在真正高风险的边界知识上
3. AI 既能拿到足够多的技术事实，又不会被错误的责任边界误导

一句话总结：

**目录越靠近代码，越适合自动化；目录越靠近边界和责任，越需要人工定口径。**
