# 通用 AI Knowledge 批量生成 Prompt 模板

日期：2026-05-13

## 1. 目的

本文档提供一套可直接用于批量生成 `ai-knowledge` 文档的 Prompt 模板。

目标不是让 AI 一次性“写完知识库”，而是让 AI：

1. 基于固定输入材料批量起草 Markdown 知识文档。
2. 优先抽取系统边界、对象口径、流程责任、需求路由和代码落点。
3. 在材料不足时显式标记“待人工确认”。
4. 最终产出可以直接保存到知识树中的文件内容。

## 2. 通用批量生成总 Prompt

```text
你现在的任务是：基于我提供的材料，批量起草一组面向 AI 检索和理解的业务知识文档，输出为多个 Markdown 文件。

严格遵守下面规则：

1. 只能依据我提供的材料输出，不允许凭常识补全业务边界、责任归属、事实来源或实现方式。
2. 如果材料不足以支持某个判断，必须明确写“待人工确认”或“不足以确定”，不能伪造确定性结论。
3. 文档是给 AI 检索和理解用的，不是给人培训用的。不要写解释性话术，如“本文档用于”“帮助 AI 理解”“本节作用是”。
4. 每篇文档必须原子化，只围绕单一对象展开。
5. 尽量使用表格表达：系统职责、字段来源、责任归属、步骤责任、需求路径。
6. 如果材料中存在冲突信息，必须在对应文档中单独列出“冲突信息”，并标记“待人工确认”。
7. 不要输出额外分析过程，不要输出任务说明，只输出文件内容。
8. 每个文件必须包含：
   - 文件路径标记
   - Frontmatter
   - 标题
   - 正文
9. 输出多个文件时，严格使用下面格式：

=== FILE: <相对路径> ===
<Markdown 内容>

10. 除非我特别要求，不要省略你认为“重复”的文件。只要在目标文档列表中，就要逐个输出。

下面是本次任务信息。

【知识库根目录】
ai-knowledge/wiki/

【本批次目标文档】
<我会在这里给出文件列表>

【可用材料】
<我会在这里给出需求文档、架构文档、接口文档、代码分析结果、历史案例等>

【输出要求】
1. 仅输出文件内容
2. 每个文件使用 === FILE: ... === 包裹
3. 材料不足的地方显式写“待人工确认”
```

...

【输出要求】

2. 材料不足的地方显式写“待人工确认”

## 4. Claude Code 仓库内运行时，哪些材料可以不用手动输入

如果你是在 Claude Code 中，直接从某个代码仓库根目录启动，然后让 AI 生成知识文档，那么下面这些材料通常**不用手动粘贴**，可以让它先自行读取当前仓库：

1. `README.md`、`docs/`、`adr/`、`architecture/`、设计说明等本地文档
2. 代码目录结构、模块命名、入口文件、关键服务和关键模块
3. 本地 API 定义，例如 OpenAPI、Swagger、Proto、GraphQL Schema、AsyncAPI
4. 本地配置与集成声明，例如 `yaml`、`json`、`properties`、`env example`、CI 配置
5. 测试代码、测试目录、测试数据样例、联调 mock
6. 本仓库里已有的接口适配层、事件消费层、同步链路代码
7. 本仓库里的注释、示例请求、脚本、迁移文件、SQL、DDL

这些材料最适合支撑下面几类文档的初稿生成：

1. `本地代码落点`
2. `集成触点`
3. `api`
4. `流程与交接` 的本地步骤
5. `实现层次规则`
6. 部分 `术语与别名`

但下面这些材料，Claude Code **通常无法仅凭当前仓库可靠获得**，因此仍然建议你手动补充，或者允许 AI 输出“待人工确认”：

1. 外部系统真实职责边界
2. 哪个系统才是事实来源
3. 哪个团队或哪个系统拥有最终定义权
4. 跨仓库、跨团队的协作分工
5. 上游系统上线前置条件
6. 真实联调依赖
7. 业务验收口径
8. 历史误判案例
9. 仓库外部的需求文档、产品文档、业务规则文档

一句话区分：

1. **代码里看得见的实现事实**，通常可以不用你手动输入。
2. **代码里看不见的责任边界**，通常不能靠仓库自动推断。

## 5. Claude Code 仓库内运行版总 Prompt

如果是在代码仓库里直接使用 Claude Code，建议优先使用下面这个版本，而不是手动粘贴大量原始材料。

```text
你现在在一个真实代码仓库中工作。你的任务是：先从当前仓库自行收集可用材料，再批量起草一组面向 AI 检索和理解的业务知识文档，输出为多个 Markdown 文件。

严格遵守下面规则：

1. 先自行扫描当前仓库中的本地材料，包括但不限于：README、docs、架构文档、接口定义、配置文件、测试代码、关键模块代码、脚本、SQL、迁移文件。
2. 对于能从当前仓库直接确认的技术事实，可以直接写入文档。
3. 对于不能从当前仓库可靠确认的业务边界、责任归属、事实来源、前置依赖、验收口径，不允许凭常识补全，必须标记“待人工确认”。
4. 文档是给 AI 检索和理解用的，不是给人培训用的。不要写解释性话术。
5. 每篇文档必须原子化，只围绕单一对象展开。
6. 输出多个文件时，严格使用下面格式：

=== FILE: <相对路径> ===
<Markdown 内容>

7. 如果你在仓库中找不到某类材料，不要假设它存在；应在对应文档中标记材料缺失和待人工确认项。
8. 不要输出你的搜索过程，不要输出任务说明，只输出文件内容。

下面是本次任务信息。

【知识库根目录】
ai-knowledge/wiki/

【本批次目标文档】
<我会在这里给出文件列表>

【可额外补充的仓库外材料】
<如果我有需求文档、架构图、外部接口文档、历史案例，再补给你；没有就留空>

【输出要求】
1. 先用仓库内材料起草
2. 仓库外材料没有提供时，涉及边界结论的地方标记“待人工确认”
3. 每个文件使用 === FILE: ... === 包裹
```

## 6. 第一批：原子事实卡批量生成 Prompt

```text
基于下面材料，批量生成第一批原子事实卡。

【目标文档列表】
1. 业务全景/系统地图.md
2. 外部系统/<外部系统A>.md
3. 外部系统/<外部系统B>.md
4. 业务对象与口径/<核心业务对象A>.md
5. 业务对象与口径/<核心字段或状态A>.md
6. 业务能力/<核心能力A>.md
7. 业务能力/<核心能力B>.md

【生成要求】
1. 系统地图必须包含系统清单表格，字段包括：系统、类型、负责内容、不负责内容。
2. 外部系统卡必须包含：职责、非职责、与本地系统关系、变更判断、本地不可做的事。
3. 业务对象卡必须包含：概念定义、事实来源、本地存储身份、语义边界、常见混淆项。
4. 业务能力卡必须包含：能力定义、系统归属、改动类型、相关代码落点。
5. 所有“谁负责”“以谁为准”“本地是否可定义”这类结论，若材料不足，必须标记“待人工确认”。

【可用材料】
<粘贴你的原始材料>
```

2. 流程与交接/<核心流程B>.md

8. 本地代码落点/<关键模块B>.md

【生成要求】

## 10. 批量生成后的自检 Prompt

```text
你现在不是继续生成文档，而是审查下面这批已生成的知识文档。

任务：
1. 找出哪些结论是有明确材料支持的。
2. 找出哪些结论只是推测，应该改成“待人工确认”。
3. 找出哪些文档之间存在冲突。
4. 找出哪些关键知识缺失，导致 AI 后续无法稳定生成准确 Plan。

输出格式：
1. 确定性结论
2. 待人工确认项
3. 冲突项
4. 缺失项
5. 建议补充的文档

审查重点：
- 系统边界
- 事实来源
- 能力归属
- 是否需要改本地代码
- 本地改动范围
- 前置依赖
- 验收标准

【待审查文档】
<粘贴已生成文档>
```

## 11. 推荐生成顺序

建议按下面顺序执行：

1. `业务全景`
2. `术语与别名`
3. `外部系统`
4. `业务对象与口径`
5. `业务能力`
6. `流程与交接`
7. `集成触点`
8. `api`
9. `需求路由`
10. `实现方式判断`
11. `本地代码落点`
12. `前置依赖与协作`
13. `规则与反例`
14. `验证与验收`
15. 最后再生成 `index.md`、`doc-map.md`、`getting-started.md`

原因是：

1. 先生成原子事实卡。
2. 再生成流程和技术映射。
3. 再生成需求决策卡。
4. 最后生成导航和入口文档。

## 12. 占位符替换说明

上面各批次中的 `<...>` 都是占位符，落到真实公司项目时应替换为你的真实业务名称。

建议替换规则如下：

1. `<外部系统A>`：一个在需求中常被提及、但通常不由本地仓库直接修改的系统。
2. `<本地系统或服务A>`：你方真正承担同步、编排、查询、展示或适配职责的本地系统。
3. `<核心业务对象A>`：需求里高频出现、且存在明确语义边界的对象，例如主数据实体、交易单据、资格对象、结算对象、库存对象。
4. `<核心字段或状态A>`：经常决定事实来源和责任归属的字段、状态或规则名。
5. `<核心能力A>`：一类可被业务和技术共同识别的能力，例如主档同步、资格计算、状态流转、统一查询。
6. `<核心流程A>`：一条端到端责任链路，例如“上游变更进入本地同步链路”“本地查询结果对外暴露链路”。
7. `<高频需求类型A>`：真实需求中反复出现的变化类型，例如“外部系统新增字段”“上游规则变化”“本地筛选条件新增”“接口返回字段扩展”。
8. `<前置依赖主题A>`：跨多个需求重复出现的阻塞条件，例如“上游字段上线前置条件”“联调环境依赖”“权限与白名单依赖”。
9. `<核心场景A>`：你们真正需要验收的业务场景，而不是泛化测试主题。

如果一个项目还不知道该填什么，不要让 AI 自己造名称。应先从真实需求、架构文档、接口文档和代码分析结果里抽取候选名称，再替换占位符。

## 13. 推荐实际跑法

如果要在真实公司项目中直接使用，建议按下面批次执行：

1. 第一轮：批量生成系统卡、对象卡、能力卡。
2. 第二轮：人工快速修正外部系统边界、事实来源和主责归属。
3. 第三轮：批量生成流程卡、触点卡、API 卡、本地代码落点卡。
4. 第四轮：批量生成需求路由卡、实现方式判断卡、规则卡、误判案例卡、验收卡。
5. 第五轮：批量生成导航文档。
6. 第六轮：使用自检 Prompt 做一轮候选知识复核。

## 14. 关键附加约束

每次跑批量生成时，建议额外附加下面这条约束：

```text
如果某个结论只来自代码结构、命名、接口字段，而没有业务材料明确支持，请保留技术事实，但不要直接上升为业务责任结论。
```

这条约束会明显减少“内容完整但边界全靠猜”的问题。
