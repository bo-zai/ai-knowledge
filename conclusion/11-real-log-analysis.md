## 分析方法

读取 CoPaw 项目下的真实开发对话日志（JSONL 格式），提取：
- 用户需求类型

共分析约 10 个主要 session，覆盖以下需求类型。

## 知识缺口分析

从真实日志中，Agent 需要但无法从代码获取的信息：

### 1. 业务含义缺口

**场景**：用户问"运营看板 5 个卡片的查询口径分别是什么"

Agent 能做的：
- codegraph 找到 `_get_branch_breakdown` 等方法
- Read 读方法体，看到 SQL 查询逻辑

Agent 不能做的：
- 知道"口径"在业务上是什么意思
- 知道为什么用这个 SQL 而不是另一个
- 知道统计结果的业务用途

**这个缺口只能问用户**。

### 2. UI 设计决策缺口

**场景**："技能卡片增加创建和更新时间"

Agent 能做的：
- Glob 找 SkillCard.tsx
- Read 读现有结构
- 知道 last_updated 字段存在

Agent 不能做的：
- 决定时间展示位置（卡片头部？底部？）
- 决定展示格式（绝对时间？相对时间？）
- 决定配色方案

**Agent 用 AskUserQuestion 问配色方案**。这是设计决策，代码中没有答案。

### 3. 浏览器/外部系统限制

**场景**："Clipboard API 报错"

Agent 能做的：
- Grep 找 clipboard.ts
- Read 读代码，看到 clipboard.writeText 调用

Agent 不能做的：
- 知道浏览器 Permissions Policy 是什么
- 知道哪些 iframe 配置会阻止 Clipboard API
- 知道本项目 iframe 的具体配置

**这个信息在代码之外**，需要搜索 Web 或问用户。

### 4. 组件状态流（前端特有）

**场景**："删除后上传文件详情不展示"

Agent 能做的：
- Read 读 SkillItem.tsx 的状态管理
- Read 读上传逻辑

Agent 不能做的：
- 理解多个组件间的状态同步机制
- 知道 React 状态更新的时序问题

**这个缺口需要读更多组件代码**，但不是知识库能预先提供的信息。

## 知识库能提供什么？

从真实日志分析，知识库可能在以下场景有增量价值：

### 有价值的知识类型

| 知识类型 | 能帮的场景 | Agent 原来的做法 |
|---------|----------|----------------|
| **业务概念定义** | "口径"是什么、"分行"对应什么数据源 | 问用户 |
| **UI 组件结构概览** | 快速知道技能卡片有哪些组件组成 | 多次 Read 不同文件 |
| **外部系统限制** | Clipboard API 的 Permissions Policy 限制 | WebSearch 或问用户 |
| **API 用途说明** | userInfo API 返回什么、用于什么场景 | Read API 文件推断 |

### 无价值或低价值的知识类型

| 知识类型 | 理由 |
|---------|------|
| **调用链知识** | Agent 用 codegraph 实时追踪，比预生成更准确 |
| **方法签名** | Agent 用 Read/codegraph 直接获取 |
| **UI 设计决策** | 需要问用户，知识库无法预知用户偏好 |
| **Bug 复现步骤** | 每次 Bug 不同，无法预生成 |

## 与理论分析的对比

之前理论分析认为 4 类知识有价值：
1. 跨文件综合型概念知识
2. 跨域业务流程
3. 约束的过滤
4. 能力域地图

真实日志发现：

| 理论知识类型 | 真实场景验证 |
|------------|------------|
| 跨文件概念综合 | **部分验证** — "口径"概念需要，但 Agent 更多是问用户 |
| 跨域业务流程 | **未验证** — CoPaw 是前端项目，没有后端跨域流程 |
| 约束过滤 | **未验证** — 前端项目没有业务 throw |
| 域地图 | **低价值** — Agent 用 Glob/Read 快速找到组件 |

**真实日志揭示的新知识类型**：
- UI 组件结构概览（前端项目特有）
- API 用途说明（前后端通用）
- 外部系统限制（浏览器、第三方 SDK）

## 结论

### 知识库真正有用的场景

从 CoPaw 真实开发日志看，知识库的增量价值在于：

1. **业务概念解释** — 当代码中的术语（如"口径"、"分行"）无法从代码推断时
2. **组件结构概览** — 减少 Read 多个文件的成本（前端项目特有）
3. **外部系统限制** — 代码之外的浏览器/SDK 限制

### Agent 更常用的做法

Agent 在真实开发中更常用的做法是：
- **问用户**（UI 设计决策、业务含义）
- **Read/Glob**（前端组件探索）
- **codegraph**（后端调用链追踪）

知识库是补充，不是首选。

### 建议

基于真实日志分析，知识库生成应聚焦：

1. **前端组件结构概览** — 每个页面有哪些组件、组件间数据流
2. **API 用途说明** — 每个 API 的业务用途、调用场景
3. **业务术语表** — 项目特有的业务概念定义

不应生成的：
- 调用链知识（codegraph 实时获取）
- UI 设计决策（需问用户）
- Bug 修复知识（无法预生成）

## 补充：复杂实现场景（code-memory 项目）

### 场景描述

用户需求是"实现 AI Knowledge 第一阶段能力"，包含：
- 详细的实现边界（只做什么、不做什么）
- 明确的约束（输出目录、多仓库支持）
- 指定要读的文件列表
- 实现方向建议

这是一个典型的"用户已规划好，Agent 执行实现"场景。

### 工具调用统计

| 工具 | 调用次数 | 说明 |
|-----|:-------:|------|
| Read | 289 | 大量阅读现有代码理解架构 |
| Edit | 22 | 实际修改代码 |
| AskUserQuestion | 3 | 少量确认 |
| assistant 消息 | 28 | 多轮对话 |

### 关键发现

1. **用户提供了详细的需求文档** — 包含实现边界、约束、建议步骤
2. **Agent 大量 Read** — 理解现有代码结构，不是从知识库获取
3. **少量 AskUserQuestion** — 用户需求足够详细，只需少量确认
4. **知识库对此类场景几乎无用** — 用户已提供所有必要信息

### 知识库的局限性

这个场景揭示了一个重要问题：**当用户提供了详细需求文档时，知识库完全多余**。

Agent 的工作流程是：
1. 读用户指定的文档
2. 读用户指定的现有代码入口
3. 理解约束和边界
4. 开始实现

**预先生成的知识库无法替代用户提供的具体约束**。比如：
- "第一阶段只生成一个文件" — 这是用户决策，无法从代码推断
- "不要重构现有 WikiGenerator" — 这是实现策略，无法预生成
- "输出目录必须是 ai-knowledge/" — 这是设计决策

## 最终结论

### 知识库真正有价值的场景（从真实日志验证）

| 知识类型 | 验证结果 | 适用场景 |
|---------|:-------:|---------|
| 业务概念定义 | **部分验证** | 用户问"口径"等业务术语时 |
| UI 组件结构概览 | **验证** | 减少 Read 多个前端组件的成本 |
| API 用途说明 | **验证** | 快速理解 API 的业务用途 |
| 外部系统限制 | **验证** | Clipboard API 等代码之外的限制 |

### 知识库无价值或低价值的场景

| 知识类型 | 验证结果 | 理由 |
|---------|:-------:|------|
| 跨域业务流程 | **未验证** | CoPaw 是前端项目，无后端跨域 |
| 约束过滤 | **未验证** | 前端项目没有业务 throw |
| 能力域地图 | **低价值** | Glob/Read 足够找到组件 |
| 复杂实现约束 | **无价值** | 用户需求文档已提供 |
| 调用链知识 | **无价值** | codegraph 实时获取更准确 |

### 建议：知识库应聚焦什么

基于真实日志分析，知识库生成应聚焦：

1. **业务术语表** — 项目特有的业务概念定义（如"口径"、"分行"）
2. **UI 组件结构概览** — 前端项目特有，减少 Read 成本
3. **API 用途说明** — 每个 API 的业务用途，不是签名
4. **外部系统限制** — 浏览器/SDK 限制，代码之外的信息

不应生成的：
- 实现约束和边界（用户需求会提供）
- 调用链知识（codegraph 实时获取）
- UI 设计决策（需问用户）
- Bug 修复知识（无法预生成）
