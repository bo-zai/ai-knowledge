# AI Agent 视角下的知识库价值分析总结

本文汇总了从 AI Agent 真实工作流出发，对 ai-wiki 设计文档中 9 类知识的价值评估。

## 分析方法

模拟 AI Agent 收到 8 种不同类型需求后的真实工作过程：

- 单域新功能、跨域 Bug 修复、跨域新功能
- 重构、外部集成、模糊需求、性能问题、配置变更

在每个场景中，记录 Agent 实际会执行的操作（CodeGraph 调用、Grep、问用户），然后判断预生成的知识库在哪些环节提供了 CodeGraph 无法替代的增量价值。

## 核心发现

### 发现 1：CodeGraph 覆盖了 Agent 80% 的信息需求

Agent 的主要工具是 CodeGraph 的四个能力：

- `context(自然语言)` → 一次返回入口、相关符号、关键代码
- `explore(多个符号)` → 一次看多个类的源码
- `callers` / `callees` → 追踪调用链
- `impact` → 分析变更影响半径

这些工具使得很多"无知识库时需要多步操作"的信息，实际上 1~2 次调用就能获取。

### 发现 2：Agent 的工作模式是"CodeGraph 优先，知识库补充"

Agent 不会"先读完知识库再工作"。真实模式：

```
CodeGraph context/explore → 理解代码 → 遇到障碍 → 查知识库（如果知道它存在）
                                                → 或问用户（更快更准）
```

知识库是补充工具，不是起点。

### 发现 3："问用户"在很多场景下优于查知识库

面对模糊需求、不确定的业务含义、代码之外的运维信息时，问用户比查知识库更直接有效。知识库的价值还要再打折——有些"知识库帮了忙"的场景，Agent 可能直接问用户了。

### 发现 4：知识库真正不可替代的信息只有三类

| 知识类型                               | 为什么 CodeGraph 替代不了                                             |
| -------------------------------------- | --------------------------------------------------------------------- |
| **跨文件综合型概念知识**               | CodeGraph 给单个类的全貌，但不能说"A 类和 B 类共同构成'课件类型'概念" |
| **跨域业务流程**                       | CodeGraph trace 在 @EventListener 处断裂，追踪不了异步全链路          |
| **约束的过滤（业务约束 vs 工程惯例）** | CodeGraph 找到所有 throw，但分不清"参数校验"和"业务规则"              |

## 8 个场景的结论汇总

| 场景             | CodeGraph 覆盖率 | 知识库增量价值最高的类型       | 知识库增量价值 |
| ---------------- | :--------------: | ------------------------------ | :------------: |
| 01 单域新功能    |       ~85%       | 跨文件概念综合、约束过滤       |     低~中      |
| 02 跨域 Bug 修复 |       ~90%       | 约束（频率限制等）             |       低       |
| 03 跨域新功能    |       ~75%       | 跨域流程（竞态条件）、概念知识 |       中       |
| 04 重构          |      ~100%       | 无                             |       零       |
| 05 外部集成      |       ~90%       | 边界知识（配置是否有效）       |       低       |
| 06 模糊需求      |       ~85%       | 无（问用户优先）               |       低       |
| 07 性能问题      |       ~95%       | 无                             |       零       |
| 08 配置变更      |       ~90%       | 边界知识（配置有效性）         |       低       |

## 知识类型的最终评估

### 有不可替代价值

| 知识类型                 | 不可替代的场景        | 不可替代的信息                                       |
| ------------------------ | --------------------- | ---------------------------------------------------- |
| 概念知识（跨文件综合型） | 几乎全部场景          | "A 类和 B 类共同构成概念 X"、"概念 X 和 Y 的区别"    |
| 跨域业务流程             | 跨域新功能（场景 03） | 异步触发链路、竞态条件、端到端路径中的关键分支       |
| 约束知识（过滤后）       | 新功能、Bug 修复      | "这是业务规则不是工程惯例"、"这个约束作用于哪些能力" |

### 有价值但可被替代

| 知识类型             | 可被什么替代                                                             |
| -------------------- | ------------------------------------------------------------------------ |
| 能力目录的域级上下文 | CodeGraph context 用自然语言搜索基本可替代                               |
| 边界知识             | 大多数可从代码中发现（if 分支 + 配置值）；"配置有效性"等运维信息需问用户 |
| 外部系统交互         | CodeGraph explore 可看到 SDK 集成方式；交互目的可从代码推断              |
| 数据模型聚合         | CodeGraph explore DO 类可看到外键和关联                                  |

### 无增量价值

| 知识类型               | 理由                                                     |
| ---------------------- | -------------------------------------------------------- |
| 能力关系的调用链       | CodeGraph trace/callers/callees 实时数据更好             |
| 操作列表               | CodeGraph explore Controller 即可                        |
| 架构概览（大部分字段） | CodeGraph search + node 即可获取项目类型、技术栈、启动类 |
| 索引体系               | 条目少时 Glob 即可导航                                   |

## 真实日志分析的关键发现

从 CoPaw 和 code-memory 项目真实开发日志分析，得出以下关键结论：

### 真实需求类型分布

| 需求类型    | 典型 Session          | Agent 工具使用模式                             |
| ----------- | --------------------- | ---------------------------------------------- |
| UI 功能开发 | 技能卡片时间展示      | Glob → Read → AskUserQuestion（设计决策）      |
| 调查类需求  | 运营看板口径调查      | codegraph → Read → 问用户（业务含义）          |
| Bug 修复    | Clipboard API 报错    | Grep → Read → WebSearch（外部限制）            |
| 复杂实现    | AI Knowledge 第一阶段 | Read 289 次 → Edit 22 次（用户已提供详细需求） |

### 知识库真正验证有价值的类型

| 知识类型        | 验证结果 | 理由                           |
| --------------- | :------: | ------------------------------ |
| 业务术语表      | **验证** | "口径"等业务概念无法从代码推断 |
| UI 组件结构概览 | **验证** | 减少 Read 多个前端组件的成本   |
| API 用途说明    | **验证** | 快速理解 API 的业务用途        |
| 外部系统限制    | **验证** | Clipboard API 等代码之外的限制 |

### 知识库无价值或低价值的类型

| 知识类型     |  验证结果  | 理由                         |
| ------------ | :--------: | ---------------------------- |
| 跨域业务流程 | **未验证** | CoPaw 是前端项目，无后端跨域 |
| 约束过滤     | **未验证** | 前端项目没有业务 throw       |
| 能力域地图   | **低价值** | Glob/Read 足够找到组件       |
| 复杂实现约束 | **无价值** | 用户需求文档已提供详细约束   |
| 调用链知识   | **无价值** | codegraph 实时获取更准确     |

### 核心结论

**理论分析与真实日志的主要差异**：

- 理论分析低估了"问用户"的使用频率
- 理论分析低估了 Read/Glob 的覆盖能力
- 理论分析高估了知识库的增量价值
- 真实日志揭示了新知识类型：UI 组件结构、API 用途、外部限制

**最终建议**：知识库应聚焦业务术语表、组件结构概览、API 用途说明、外部系统限制。不应生成调用链、设计决策、实现约束等类型。
